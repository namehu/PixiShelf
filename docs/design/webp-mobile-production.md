## 实现边界

- 保守快速路径仅接受全画布、不透明、不清除的独立 VP8 帧（flags 为 0 或 2；不透明画面的混合结果完全覆盖前帧）；每帧检查，不预下载全文件判断。其他语义留给现有 libwebp 动画合成器。
- 维持一个原媒体请求。快速路径按输入预算保存压缩数据，供循环与中途顺序重建使用；不缓存整段 RGBA。回退重建时已输出帧只用于恢复合成状态，不重复显示。
- 快速路径按 RIFF 声明尺寸、压缩长度和 WASM/输出/临时空间预算选择；不满足时原路径处理，不扩大总体预算。
- 独立帧双 Worker 四额度；Worker 输出附带媒体时间。播放时钟与解码吞吐分离；实际输入不足暂停时钟，落后才省略可安全跳过的解码，首帧和末帧必须显示。
- 原生 ImageDecoder 仍是后续候选，本轮不同时引入第二套生产后端。
- 保留旧调度诊断作为对照，不把实验阶段的测试文件或 profile 产物作为生产依赖。

## 实现细节

- RIFF/VP8X/ANIM 标准前缀、每个 ANMF 的完整画布/不透明/无清除（flags 为 0 或 2）、VP8 编码尺寸及边界逐项检查。ANMF 内的 VP8L、ALPH 或局部、清除等不合格帧退回现有动画合成器，未扩大像素/文件总预算。标准前缀后的未知 FourCC 块可按容器规则跳过，仍校验长度、零填充和有效 EOF；头部已声明 ICCP、EXIF、XMP 的文件仍不进入快速路径，未声明的对应块可跳过；动画顶层 ALPH、VP8、VP8L 或重复 VP8X 直接报告 invalid；重复 ANIM 仅在含填充的长度至少为 6 字节时跳过，不覆盖首次 ANIM 的循环设置。未知块分段跳过，不套用单帧 2MiB 限制，但仍受总输入预算约束。
- 预算：两个各 128MiB 的 WASM 堆 + RIFF 声明压缩长度 + 8MiB 输入块余量 + 六个 2MiB 帧临时余量 + 五幅 RGBA（四输出与可见 Canvas），总和必须在 maxManagedBytes 内；maxHeapBytes 至少容纳两个堆。否则原路径。
- 单压缩帧超过 2MiB 时转顺序路径；快速路径实际输入块超过 8MiB 时报告预算错误。压缩预读最多四帧，累计达到 2MiB 停止继续读取。已收原媒体以 64KiB 块保留，防止小网络块造成无界对象数量；单轮自动浏览也保留全部已收压缩输入，供顺序重建使用。四帧／2MiB 只限制待解码队列，不是总输入或总内存上限；压缩输入上限为窄屏 128MiB／宽屏 256MiB，并继续受总预算约束。
- 只在待解码帧已过期时根据实际媒体时钟和解码 EWMA 省略安全帧，预测最多 100ms。已有输入中的过期候选继续扫描；不为了等待未来预测帧而停住当前解码。
- 原生 C 合成器未改，只在固定构建中导出 libwebp 已有的 WebPGetInfo / WebPDecodeRGBAInto；预编译及原生 ASan/UBSan/差分检查已重建通过。独立子 Worker 纳入内容版本 hash 和应用资源复制。
- 诊断增加 pipeline、fallbackReason、decodeOmittedFrames；legacy 调度仍使用顺序路径，decodeStrategy=sequential 可用于内部对照。普通 UI 不增加缓冲/loading 提示。
- 中途依赖回退需要重放解码已收帧以恢复画布，停顿可能达到数秒，随回退位置、帧复杂度和设备吞吐增加；不输出已交付帧，也不重发媒体 HTTP 请求。回退预留压缩与输出内存，可能比直接走原路径更早触及内存门禁，不承诺所有依赖链都实时。

### 持续播放修正方案（2026-10-12，实验中）

先做独立帧路径可对照实验，通过手机长时测量后再决定生产接入；生产默认行为、C/WASM 和源媒体不变。

1. **画质与语义。** 保留原尺寸、颜色和所选帧的像素；只在现有门禁确认独立后省略解码，依赖帧仍走原合成器。媒体时间、首末帧、有效 EOF、循环、暂停续播和实例隔离不变。降低的是时间采样密度，不能宣称与原 60fps 动作细节完全相同。
2. **估算持续负载。** 实验用首批最多 32 个归一化帧时长估算源帧率，至少 8 次实际解码后开始决策，解码耗时 EWMA 权重 0.1。源帧率超过 45fps 且 `源帧率 × 平均解码ms / (2 × 1000) > 0.65` 时选择约 30fps；否则保留原帧率，继续观察耗时。0.65 是两个 Worker 的服务耗时余量草案，不是测得的 CPU 利用率或温度，也不是已验证最优阈值。当前手机冷机 33ms／60fps 已约为 0.99，因此这一组实际是校准后即降到约 30fps，用前段动作采样换持续负载余量；不是热后才降。桌面 11ms 不触发，原 24／30fps 文件不因此进一步降低帧率。首帧长停留可能压低前 32 帧均值，当前三张不受影响；生产化前补此类素材及滚动估计验证。
3. **先选帧再解码。** 使用媒体时间上的约 33.33ms 网格，允许容器毫秒舍入误差；保留覆盖目标时间的源帧，不合成新画面、不插帧。确认后继后才省略旧候选，末帧及循环边界保留。候选已修正 `needsSuccessor`：只有非首帧、尚未确认末帧且 `frame.endMs ≤ due + 0.5` 时才等待后继；已经覆盖目标时间的帧立即允许解码，不能因未来网络数据未到而额外等待。已有迟到省略机制继续兜底。单个实例只降不升，避免反复切换；跨素材重新测量。仍为两个 Worker、四个输出额度及原压缩队列预算，不增加缓存或并行。
4. **本地验证。** 可控时间覆盖均匀／不均匀时长、快慢解码、低帧率、首末及循环边界；真实 Worker/WASM 使用合成素材，将选中帧逐字节对照完整顺序合成。补充暂停、循环、截断和停止后旧事件检查。原始实验代码和数据放 Git 忽略目录，暂不积累生产实验入口。
5. **手机验收。** 改为现状、提前降载（0.65）、持续高负载后降载三组，每组至少十分钟。第三组规则草案：同一估算比值 ≥0.95 持续累计 8 秒有效播放后降至约 30fps；输入等待和暂停不累计，低于阈值重置累计，高负载累计及已降级状态跨同一连续测试会话的切图保留，避免每张约五秒重置导致永不触发。第三组及跨切图计时已实现并完成本地验证；每张图重新校准期间保留前次累计但不增加未知负载时间。0.95 在当前冷机也可能超过，所以第三组是延迟降载，不是温度检测或“真正发热才降”的保证。正式接入前还需定义不同素材及长时间闲置后的策略恢复。

   Mate 40 Pro／Via，同三张、同 USB HTTP、同屏幕设置，各组之间冷却并记录实际起始状态；三组串行、与构建分开。分别报告首分钟和末三分钟的解码耗时、绘制数、间隔 P50／P95／最大值、省略数、触发降级时间、输入等待、温控／频率、异常和内存。当前样本输入充分时目标墙钟 ≤5574ms，间隔 P95≤50ms、最大≤150ms。提前／延迟降载组要同时比较前段动作采样损失与末段稳定性，不以帧数更少本身认定观感更好。固定顺序不是随机试验；差异不清楚时倒序复测。ADB 温控仅用于外部验收；人工动作观感单列，未经用户确认不标通过。
6. **独立排查生产输入等待。** 跟踪实际同源原图请求的最终地址是否一致（含版本参数）、重定向、状态、实际响应缓存头及完整读取／中止情况；区分首次、完整读完后立即重播、切图回来及刷新重播。仓库图片接口含 immutable／ETag，只证明缓存策略允许复用，不证明线上头部一致或 Via 命中，更不能据文件约 20MiB 推定缓存上限。若可取得同源 Resource Timing，记录 transferSize／encodedBodySize／decodedBodySize、请求至响应及响应结束耗时，并与浏览器网络证据或访问日志交叉核对；缺字段或不可观测即标未知。Worker 内请求不能假设能从窗口 timing 表读到。必要的诊断只输出匿名关联信息，不导出地址或凭证。

   现有 bufferingMs 是 buffering 状态累计，readWait 包含流读取和调度，并非两个可直接相加的纯网络阶段。8.02−3.47≈4.55 秒，并不等于 5.067 秒媒体时长，所以不能据此精确分摊慢播；需补时间轴实际被输入范围截住的时长、网络接收／已接收待解析的区分。此线不与 USB 降载结果混为一谈，USB 通过后仍须线上复核。可补热状态下立即刷新对照，但记录刷新间隔和前后温控，避免把冷却误判为清理页面资源。

### 1. 节奏核对与生产策略

发现两个可独立复现的问题，不能由旧报告的 P95 唯一反推手机每一帧的原因：

- **时间舍入与刷新相位。** 当前样本的帧时长重复 17／16／17ms，降载选帧的起点为 0／33／67／100ms。真实 `WebpPlayer.tickMedia` 在可控 60Hz、四额度、供帧充分时，能画完全部 153 张选中画面，却产生 17／33／50ms 间隔；将回调相位移动 4ms，稳态 P95 从 50ms 变为 33.33ms。没有网络或解码不足也会发生。此为 Canvas 调用时刻，不是屏幕测量。
- **旧实验切换网格错误。** `due + 33.33ms` 与全局网格取最大值混用了两种相位。先派发 11 帧再启用降载，可以在源帧选择中产生 17／50ms 间隔；改 RAF 相位也不能消除。问题位于忽略目录中的实验调度器，不能描述为已发布降载逻辑的缺陷，因为生产尚未启用该逻辑。

生产接入选择：**保留前段原帧率，持续高负载后降到约 30fps，同时修正节奏。** 两种降载均已满足三张样本的十分钟数值门槛；选延迟方案是为了保留冷机前段的动作采样，不是因为它的旧 P95 更低。提前降载保留为诊断对照，不作为首选。

1. 独立路径使用滚动最多 32 帧的归一化时长均值估计源帧率；至少 8 次解码测量。采用实验中的服务耗时 EWMA（新值权重 0.1），估算比值 `源 fps × EWMA / (2 × 1000)`。源 fps >45 且比值 ≥0.95，持续累计 8 秒有效媒体推进后触发。暂停、输入冻结和校准期不累加；低于阈值或低帧率重置高负载累计。首帧长停留会暂时影响均值，滚动窗口前进后可恢复判断。数值是当前证据下的初始参数，不是 CPU 利用率、温度或所有设备最优阈值。
2. 同一次连续预览跨切图保留高负载累计／降载锁定；新素材先判断帧率，≤45fps 不再减半。关闭预览、换作品或退出账户重置；停止或隐藏超过 60 秒只使**下一个播放尝试**重新校准，不在正在暂停的实例中途升档。同一实例只降不升，恢复暂停保留原时钟。循环以累计媒体时间计，不因每轮归零而永远触发不了。
3. 降载使用整数槽号 `n`，目标为 `cycleStart + n × 1000/30`，切换时对齐一次，此后不把已舍入的源帧起点反复加进网格。仍仅省略验证独立的帧；首末帧、循环边界、输入等待与回退语义保留，`needsSuccessor` 不阻塞覆盖当前目标的帧。
4. 为降载输出新增可选 `presentationMs`，将“选取哪个源画面”与“何时呈现该画面”区分开。普通降载帧取 `max(sourceStartMs, gridMs + 0.5ms)`；首末帧保留原起点。0.5ms 与选帧的容器舍入容差一致，禁止未来画面提前显示。长停留按源帧区间处理，不重复解码来凑网格。主线程的到期比较／省略比较一起使用该时间；媒体进度、时长、EOF 仍用原始起止时间，不能通过改写媒体时长修饰数据。
5. 不缩分辨率、不降低解码精度、不插帧；仍双 Worker／四额度。时间网格不能保证任意刷新率和回调抖动下每次都恰好 33.33ms，也不能克服实际解码吞吐不足。

匿名模型复测：切换点 0–32，30／60／90／120Hz，8 种相位共 1056 组，统一网格及显示时刻后的稳态 P95 均为 33.33ms；另有 20／59.94／75Hz、回调抖动、长停留与不均匀帧测试，明确保留实际抖动，不承诺其消失。模型不包含真实解码、背压或输入，不能替代整合后的手机验收。旧三组报告没有逐帧原始轨迹，不能定量分摊其中有多少来自上述两个因素。

### 2. 压缩输入复用

**目标是同一作品内完整下载后的重播和回看，首次播放保持流式。** 第一版仅接入作品详情的活动预览；列表多个播放器和其他页面不自动共享。缓存保存原始压缩字节，不保存 RGBA，不改服务端缓存头，不持久化到 sessionStorage／IndexedDB，不后台预下载下一张。

| 项目 | 选定规则 |
| --- | --- |
| 容量 | 每个标签页最多一个活动预览缓存；缓存池配置上限 128MiB，单条最多 64MiB，最多 8 个条目。以字节和当前播放预算为主要限制，不固定为三张；实际容量按下文公式收缩。包括完整、正在构建和借用中的条目，不为每个播放器重复分配。此为待实测的初始配置，不是已测得的浏览器极限。 |
| 计费 | 按 64KiB backing buffer 实际容量计费；下载前预留整个候选容量，提交时不再复制整份。当前三张按块计费共 60MiB，可容纳 14→15→16→14。 |
| 准入 | 同源媒体 API、完整 HTTP 200、明确且合法的 Content-Length ≤64MiB、与 RIFF 长度一致，最小 44 字节头部通过现有 independentHeader 检查及预算，并有现有 `withMediaVersion` 生成的版本参数。无版本、未知长度、206、重定向或超限不入缓存，继续同一请求的无缓存流式通道。头部已明确需顺序路径的素材暂不缓存；先通过头部、随后遇到依赖帧的素材仍可复用。内容仍由原播放器验证，不信任客户端尺寸或长度提示。 |
| 缓存键 | 账户 + 本地登录代次 + 作品作用域 + 完整同源 URL（含版本及其他 query，去掉 fragment）。不能使用包含播放尝试编号的 `resourceKey`／`playbackKey`，否则重播永不命中；不能只用文件名。 |
| 淘汰 | 超过数量或字节额度，先删除最久未使用、未借出的完整条目；当前在读条目保留引用并继续计费。没有可淘汰空间就放弃新条目的复用，不能突破上限或中断当前播放。完整条目 5 分钟未使用即淘汰，命中更新使用时间。 |
| 生命周期 | 切图取消旧读取，未完成条目删除；当前完整条目可留下供回看。关闭预览／离开作品／pagehide 清空；隐藏时取消缓存构建、清除未借出条目，现有播放器按原规则暂停，已借用数据计费到释放。注销、切账户、已知会话失效直接关闭相关端口／实例并清空，迟到消息不得恢复条目。 |
| 提交条件 | 正文完整、字节数吻合，Worker 确认容器有效 EOF 后才由 building 变为 ready；不拿 HTTP reader.done 或数据库时长当验证通过。截断、解析／解码错误删除候选；已缓存文件再播放出错也删除。不能宣称未解码的所有 VP8 帧都已验证。 |
| 暂停／取消 | 同图暂停保留实例与输入游标；切图、销毁立即关闭旧 lease、AbortController 和端口。取消后不为填满缓存继续下载，不复用半截文件，不做断点续传。 |

**输入通道选择：一个有背压的压缩输入提供器。** 放在预览作用域中，由应用持有压缩缓存与同源 `credentials: same-origin` 请求；通过 `MessagePort` 按需向 Worker 交付原始字节。未命中时边读边播放并在额度内填充 building 条目；命中时按同一接口读取内存，不再次请求媒体正文。保留 Worker 原来的直接 fetch 作为无缓存路径，包的默认调用行为不变。不要 `response.clone()/tee()` 后分别无限读播放流和缓存流，也不要 `arrayBuffer()` 等整张下载完再开播。

- 每次传输最多 64KiB，仅一个未完成 read，流 highWaterMark=0；保守预留收发两块共 128KiB。下游取走前一块才请求后一块。命中时复制小块再 transfer，不能 detach 缓存所有的缓冲区。每次只保留一个 fetch 返回块，上限为 8MiB−128KiB；连同两块端口缓冲，无缓存时仍落在既有 8MiB 输入块额度内。暂停后不主动读流，暂停前在途读取可完成且仍计费。初始前缀、落入顺序回退的已收字节和同一个 reader 一起传递，不能因回退再 GET。首次与命中借用均通过独立端口／lease 和播放器 generation 隔离；撤销后拒绝旧消息。
- 复用池要提供 `acquire → read → release` 和 `invalidate/clear`；同一个作用域只允许一个活动播放 lease。快速切图先撤销旧 lease，再激活新 lease；慢回调不产生第二个不计费读取者。直接诊断默认绕过该池，可另开明确标注的“复用输入”测试，避免把内存成绩混成网络成绩。
- **容量按当前解码预算调整，不把 128MiB 固定预占给缓存。** 令 `L` 为既有 maxManagedBytes、`B` 为当前素材按既有门禁计算的解码预留、`T = 8MiB + 128KiB` 为桥接额外预留。缓存可用上限取 `max(0, min(128MiB, L - B - T))`，向下按 64KiB 对齐；必须同时满足 `实际缓存／构建／借用额度 + T + B ≤ L`。分配新条目前先预留并淘汰，不能先分配再检查。当前窄屏 L=432MiB 是项目自己设定的预算，**不是 Via 或手机操作系统公布的内存上限**；以后可以按真实进程内存及长测单独调整，不能用手机总 RAM 直接等同页面可用内存。
- 预算示例（不是实测 RSS）：当前三张的 B 约 327MiB，窄屏可留给缓存约 96MiB，原三张按块计费共 60MiB，仍可全部复用。若相同约 163 万像素的文件增至 50MiB，B 约 357MiB，缓存余量约 66MiB，可以保留一张 50MiB 文件供重播，但不能承诺同时保留两张。128MiB 是允许达到的上限，不是假定始终装满。已有 ReplayInput、WASM 输入副本、两块 WASM 堆、帧临时及 RGBA 仍按旧公式计入 B；缓存有原字节不代表 Worker 内不再占用输入副本。
- 读取最小头部后，在向 Worker 确认预算之前完成准入检查。若复用预留会使原本可播素材触及预算，清空旧缓存并放弃该素材复用；同一 HTTP reader 继续通过端口提供输入，Worker 保留原预算，不重新下载，也不为了缓存强迫走更慢的路径。无预览缓存选项的包调用仍由 Worker 直接 fetch。不能同时保留旧缓存还给 Worker 完整预算。服务端元数据只能用于提前保守拒绝；Worker 校验的 RIFF 尺寸／长度若不一致，缓存无效并沿用既有错误／回退规则，不抬高预算。
- 上述数字限定可归属的压缩缓冲及播放器管理预算，不是浏览器 RSS 硬上限；浏览器网络、对象开销、Canvas／GPU、GC 延迟另计。单个 fetch 块超过上限时停止缓存通道并按内存限制处理，不能先复制后才检查。后续不得把“128MiB 缓存池上限”宣传为播放器总内存，也不能仅凭低精度 JS heap 读数判断剩余容量。

代价是额外保留最多 128MiB、且受解码预算进一步约束的原始压缩数据，命中仍要把字节送入 Worker／WASM，首次读取也增加小块复制和消息开销。它减少重复正文传输，不减少 VP8 解码本身，不解决第一次网络不足，不覆盖被容量、条目数或过期策略淘汰后的全部回看，也不保证后台／跨页面仍命中。明确清除账户缓存不会代替服务端会话校验；未被客户端获知的远端撤权和未更新 URL 版本的源文件替换无法由内存缓存自行感知。若要求每次都新鲜鉴权，需要另加轻量校验请求，不能同时承诺离线命中与每次网络鉴权。

协议依据：[WHATWG Streams 背压与 tee](https://streams.spec.whatwg.org/#rs-tee)、[HTML transferable objects](https://html.spec.whatwg.org/multipage/structured-data.html#transferable-objects)。这些规范不证明 Via 的实际性能，必须实测小块消息开销。

## 发布与剩余边界

构建已将独立子 Worker 纳入资源 hash 并复制进应用静态资源目录。应用更新后刷新页面会使旧协议缓存失效并使用新资源；当前正在运行的实例不会被升级中途替换。回退应用版本即可回到旧路径，无数据库或媒体迁移。
