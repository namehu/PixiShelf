# 同艺术家作品去重方案

目标是处理同一艺术家下重复导入的整部作品，设计规模为 1,000 个作品、每作平均 500 个原媒体文件。检测按文件大小清单筛选候选，再完整计算候选文件的 SHA-256；文件哈希与作品指纹都持久化。重复检测复用有效缓存，原媒体不因检测被修改、删除、重命名或生成派生文件；普通文件读取仍可能更新文件系统的访问时间。

完整功能分两阶段交付：先完成只读检测、保留建议和持久审核结果；随后开放满足条件的可恢复清理。现有普通删除的直接 unlink 流程不直接包装成批量去重。本文是实施草案，代码依据核验于 2026-10-23；资源预算尚需实测，不表示功能已经实现。

## 已确认的工程边界

## 检测含义与范围

- 使用有效 ArtworkArtist 关系及活动、未删除作品。冻结本次作品 ID 集合和范围时间；运行中新加入的作品下次纳入，不让任务无限追赶变化。
- “原媒体重复”指全部登记原媒体文件的多重集合一致。文件名和顺序不影响判定，重复次数参与判定；例如 `[A,A,B]` 与 `[A,B,B]` 不相同。
- 图片、动画、视频统一按原文件字节比较，不解码、不抽帧、不使用感知哈希。APNG 加视频与只有视频的作品不判为完整重复。
- 标题、标签、来源、艺术家关系、系列、章节、人工排序、附属文件和旧归档版本不参与媒体摘要。因此媒体重复不等于整份收藏记录可以无损合并；清理审核必须展示相关差异。
- 缺失、不可读、零字节原媒体、超限、读取中变化分别记录为未完成原因。零媒体作品不形成重复组，不能把失败后的空清单当成功摘要。
- 首版不处理相似图、部分重叠、跨艺术家全库搜索、自动导入去重或个人数据合并。

## 两级缓存与算法

### 文件缓存

每个 Image 保存当前有效 SHA-256、算法版本、绑定的根身份和规范路径、源内容代次、文件大小、可用的高精度 mtime/ctime/dev/inode 以及实际内容读取时间。大小与高精度属性使用不会丢失精度的数据库类型和序列化方式；不使用访问时间作为失效依据。

文件属性匹配支持缓存复用，但不能证明发生过任意外部写入之后字节仍相同。[Node 的 stat 时间精度依赖平台](https://nodejs.org/api/fs.html#stat-time-values)，[NFS 属性与数据也有缓存一致性限制](https://man7.org/linux/man-pages/man5/nfs.5.html)。承诺受控写入主动失效、可观察的外部变化触发重算；提供绕过缓存的完整检查，不承诺发现保持全部可观察属性不变的外部覆盖。

应用内新增、删除、替换、同 ID 覆写及扫描发布必须接入失效协议。开始写入时阻止使用旧证据，成功后使对应缓存过期；失败或已验证回滚不能发布新哈希。只读检查失效状态与[现有写入守卫](../../packages/pixishelf/services/artwork-service/summary-source-guard.ts)协调，不能依赖某条摘要记录恰好已经存在。

缓存以 Image 为逻辑归属；同路径多引用或硬链接不擅自合并数据库媒体身份。首版不跨路径共享缓存，允许多做少量读取以简化失效。重命名可能因身份属性变化重新计算，但不会改变最终内容分组。

### 作品缓存与执行顺序

1. 按游标分页读取作品及媒体，确认当前文件属性。可靠的文件数量与排序后的大小多重集合用于分桶；只有至少两个作品的桶进入内容校验。未知或过期大小先补检，不作排除证据。
2. 候选文件优先复用有效文件缓存，缺失或失效项才读取内容。读取在短数据库事务之外进行，同一文件句柄分块计算 SHA-256，检查实际读取长度。
3. 读前、读后及最终路径分别核对身份和属性；路径原子替换、原地变更或写入状态变化使结果无效。文件哈希提交同时检查执行租约和源代次，旧任务不能覆盖新缓存。
4. 作品指纹使用版本化规范编码：域标识、算法版本、文件数量、按固定规则排序的 `(文件大小,文件SHA-256)` 清单。禁止 Set 去重，禁止含糊字符串拼接。作品结果另外绑定完整 `(Image ID,路径,源代次)` 成员快照。
5. 只有全部文件成功、有效艺术家归属与成员快照仍相同、无写入中的作品，才能原子发布完整作品结果。复核使用短事务与现有一致锁顺序，不持有事务读取几百 GB 文件。
6. 通过作品指纹分组，再核对对应规范清单；不存储作品两两关系。后续属性未变化时直接复用；增删或文件变化只重算受影响文件及作品摘要。

扫描结果必须区分已完成、未完成、已变化待重查；注明检查范围、缓存复用数量及实际重读数量。已完成只表示该次范围成功检查，不表示之后外部文件永不变化。原来未进入候选的作品没有完整文件哈希，未来进入候选时需要首次补齐。

## 资源预算与调度

N 为文件数、m 为每作品文件数、B 为本次候选实际读取字节，主要成本为 `O(N log m + B)`，外加文件系统属性访问。50 万文件的属性检查本身可能昂贵，热缓存不承诺秒级完成。最坏平均 1 MB、全部成为候选时读取约 500 GB，假设有效读取 100 MB/s，纯读取约 83 分钟，尚不含打开文件、哈希与争用。

以下是压测起点，不是性能保证或已确定配置：

| 项目     | 初始设计                                                                                             |
| -------- | ---------------------------------------------------------------------------------------------------- |
| 数据读取 | 媒体游标页约 500 条；不把全库文件装入内存、任务 payload 或进度 JSON                                  |
| 文件访问 | 属性检查并发最多 4；内容读取并发 1；多个艺术家共享限制                                               |
| 缓存提交 | 每批约 100 至 250 条，时间或字节预算达到时也提交；命中不逐条更新 lastSeenAt                          |
| 让行     | 约 10 至 15 秒或 256 MiB 后，在文件边界保存进度、让行并冷却 2 至 5 秒                                |
| 进度     | 约 10 秒聚合一次文件数、字节数、命中数和错误数，不每张图写事件                                       |
| 停滞处理 | 可从 30 秒无字节进展开始测试；单文件总预算须结合大小和实测吞吐设定，不能固定很短后把正常大视频判不同 |

[队列](../../packages/pixishelf-job-runtime/src/queue-repository.ts)的 MANUAL 档高于 SYSTEM，优先级老化不会跨档；[通用重试](../../packages/pixishelf/services/background-task/job-command-service.ts)还可能把任务提升到 RETRY。去重须有领域 start/retry 入口：认证、幂等键、发起用户写入运行记录，在事务内建立低优先执行任务；同艺术家活动任务有唯一约束，重试保持预算与优先级。客户端不能通过改 trigger 或通用 enqueue 绕过规则，也不新建执行 lane。

让行会生成领取与状态事件，不能每文件让行；缓存批次使用 fenced mutation，checkpoint 与事件按阶段和时间节流。[事件清理](../../packages/pixishelf-job-executors/src/maintenance/job-event-retention-cleanup.ts)不能假定默认启用。

## 卡读 中断与运行恢复

[Dispatcher](../../packages/pixishelf-worker/src/dispatcher.ts)取消有宽限期，现有普通 fs.read 未必能在其中返回。沿用[媒体探测子进程模式](../../packages/pixishelf-job-executors/src/maintenance/sharp-animation-probe-pool.ts)，一个受控 reader 串行处理一批文件；不为每个文件 spawn。对可能阻塞的属性检查与内容读取都设置可观察的进度和退出边界，Worker 主进程不执行无界文件遍历。

超时、取消或失租约后，停止接受结果，终止 reader 并确认 close 后才释放资源或启动替代进程。仅 Promise.race 不会中止后台 I/O。[发送 kill 信号不等于进程已退出](https://nodejs.org/api/child_process.html#subprocesskillsignal)；无法退出时停止新 reader 并暴露故障，不能不断重启累积进程。不能保证异常内核或网络挂载下立即取消。

完整且已提交的单文件哈希可复用；当前文件从头重算，不承诺跨进程保存 SHA 内部状态。尚未提交的一批可能重复读取，但不得重复发布。作品结果最后发布，不因部分文件已完成就标完整。

每批和恢复时验证根路径及身份，Pixiv 根复用[现有根标记](../features/pixiv-root-identity.md)。本地导入等没有同等持久标记的根绑定配置和本次根属性，不擅自创建或绑定身份。根消失、换挂载或身份变化时停止该 run，保留既有记录；不能将暂时空目录判成无重复、清空缓存或触发清理。合法重挂载后重新建立文件证据。

## 清理前必须满足的条件

缓存和历史匹配只产生检查建议，不直接授权永久删除。以下约束在清理功能启用前全部实现；未满足时保留只读检测与审核能力。

### 内容证据与并发操作

清理计划冻结用户选择、保留作品、待移除作品、算法版本、文件清单、内容指纹及整理数据影响。执行前仅对所选组的保留者和副本绕过缓存重新读取完整内容，同组保留者在受控窗口内只读一次。这是执行清理的额外成本，不会导致日常检测反复重读全图库。

不能只在 Worker 内加锁。先以全局 Artwork ID 对整组建立持久操作声明，保留者也参与；短事务按一致顺序认领并核对所有账户的手工整理数据。数据库唯一约束拒绝重叠计划，防止两个艺术家的任务分别保留 A 删 B、保留 B 删 A。

所有 App 上传、替换、单图或整作删除、媒体增删、扫描发布及相关元数据写入都须遵守同一声明；目录和共享引用也纳入写入协调。待移除作品不再接受新的评分、书签、喜欢或阅读写入。保留者可以正常阅读，但原媒体与归属不得在清理窗口中变化。声明不能按超时直接释放，须先确认旧执行器退出并恢复操作现场；数据库租约不能撤销文件 I/O。

重新哈希与应用声明仍不能阻止外部程序随后写文件。执行清理要求目标目录的外部同步和编辑停写；无法建立这个前提时，只提供检测与审核。文件系统快照可作为经验证的检查与恢复依据，但只读快照本身不保护实时路径，不能据旧快照直接删除仍可变化的实时文件。

### 可恢复隔离

现有非 URL 删除先 unlink 再删除数据库，出现断电或数据库失败时文件无法事务回滚。批量去重改为范围受限的可恢复隔离，不能直接循环调用现有删除接口：

1. 持久化执行意图、完整清单、原位置与隔离位置，记录可恢复的数据库状态；开始前具备匹配的备份检查点。
2. 首期仅处理独占、范围明确、无未审核附属文件的作品。隔离使用同文件系统重命名；跨文件系统、共享文件或复杂目录转单件审核，不隐式复制再删除。
3. 文件移动前作品进入受控处理中状态，正常浏览与扫描不把半完成目录当有效内容。逐步记录移动结果，使用项目已有 manifest 和持久化原则，并在目标文件系统验证落盘、目录同步和断电恢复语义；不把一次 rename 等同整部作品或数据库事务。
4. 隔离完成后保留原作品与个人数据的恢复依据，不立即 Cascade 删除。隔离位置排除在全部扫描和来源发布路径之外，防止重复入库。
5. 按每个 manifest 条目的身份与阶段恢复：原文件匹配且目标不存在可继续移动；原位置不存在且隔离文件匹配可确认已完成。同一条目两处冲突、身份不符或两处都缺失时才进入人工恢复，不能猜测覆盖；逐文件移动中两个目录同时存在是正常状态。恢复时原路径已被新文件占用也禁止覆盖。
6. 永久清理为独立阶段，重新认领保留者与隔离对象，并在外部停写前提下绕过缓存完整读取保留者，确认仍保存清理意图要求的相同原媒体多重集合。隔离件也核对身份与清单，发生变化时停止自动清理。保留者只是“仍可打开”不够：若已替换为别的内容，保留隔离件并转待审核。保护持续到物理清理结束，不必锁住整个隔离保留期。单独测试恢复与永久清理后才开放自动到期删除；保留期、容量阈值、恢复入口及到期校验失败后的恢复资格在第二阶段接口规格中固定，未固定前不开放该功能。

隔离不立即释放空间，也不能替代独立备份。低磁盘空间、数据库不可写或无法持久化清单时，在破坏性步骤前停止，不自动删隔离区腾空间。

URL 作品仅在完整归档范围已审核后复用现有回收机制。多历史 revision、独有来源或未比较附属内容默认转单独审核，不能因为当前展示媒体相同就把全部历史包当重复。去重触发的回收必须绑定清理意图，现有 PURGE_ARCHIVE 到期路径也须遵守上述保留者完整校验，不能直接按期限删除。接入前不开放 URL 去重批量回收；到期校验失败时保留原件，并提供明确的待审核和恢复资格，不能沿用“超过 7 天不可恢复”使其陷入无法恢复的状态。

### 保留建议与数据差异

唯一具有评分、书签或喜欢的副本优先保留；多份都有手工整理记录时不默认勾选移除。保护检查覆盖所有账户，但页面不暴露其他账户的具体私有标记。普通阅读历史影响推荐与删除影响摘要，不使整个已读图库失去批量处理资格。

没有手工整理时优先最近阅读，再以最早入库和稳定 ID 兜底。标题、章节、人工顺序、来源、系列等差异单独展示，不承诺自动合并；不同排序不影响重复检测，但可能影响保留决定。

共享路径、硬链接及稀疏文件不能按作品大小相加推算实际可释放空间。展示按计划路径去重的文件大小，并分开说明隔离、归档回收与真正永久删除。只保护数据库已知引用不能证明目录没有未导入媒体，首期自动范围不得包含此类不确定目录。

## 权限 数据生命周期与回滚

- start、查询、暂停、继续、审核与清理入口均沿用 Session 和资源校验；账户切换使用 expectedUserId。艺术家 ID 不等于有权提交任意路径，执行范围由服务端构造。
- 当前实例是单管理员信任域。检测结果属于图库管理事实，个人标记读取保持账户边界；跨账户保护仅返回必要资格或影响信息。
- 任务进度及 SSE 只展示必要计数与脱敏错误，不返回原始绝对路径、完整哈希清单、连接信息或不受控异常。子进程使用固定入口和结构化参数，不拼接 shell。
- 文件缓存是可重建派生数据，当前版本一条，Image 删除后可级联清理；不能从缓存 GC 推导删除原媒体。
- 检测 run/item 和当前作品结果分开管理；历史检测建议保留 30 天，活动任务、当前展示结果与审核引用不参与 GC。清理意图、恢复清单与操作审计保存独立的内容证据和必要快照，不能跟随检测历史过期或 Artwork/Image 删除级联丢失。
- 仅新增表和必要索引，通过正式 migration 部署，不在迁移中扫描或同步回填 50 万文件。验证空库与非空升级、唯一约束、索引查询计划及 capability 注册。
- 只读检测回退前停止新任务，保留派生缓存表即可；不能假设旧 Worker 自动兼容新任务。启用隔离后的回退必须完成在途恢复或保留兼容执行器，不能仅回退应用镜像。

## 验收与交付门槛

先以隔离数据库和临时媒体 fixture 验证正确性、资源界限与故障恢复；原图库不用于删除或失败注入。实际 NAS 吞吐单独做只读、有界样本测量，不能用重复小文件或页缓存命中的数字替代真实存储性能。

| 场景                                               | 必须证明的结果                                               |
| -------------------------------------------------- | ------------------------------------------------------------ |
| 改名、重排、不同重复次数、APNG 与视频组合、空作品  | 集合语义正确，没有因漏成员产生的误判                         |
| 冷缓存、热缓存、一张新增或覆写、以前未候选的作品   | 有效缓存无内容重读；只补必要哈希，按实际字节统计             |
| 属性不变的外部覆盖、时间精度低、NFS 延迟           | 清楚区分缓存检查与完整重读；不声称普通缓存能证明绝对新鲜     |
| 读中原地写、路径原子替换、增加或删除成员、归属变化 | 不发布混合内容或过期作品结果，旧任务不能覆盖新缓存           |
| 共享路径、硬链接、路径越界、符号链接、根换挂载     | 不扩大访问和操作范围，不错误合并身份或自动清库               |
| 50 万媒体记录、候选很少与全部候选                  | 内存有界、SQL 无逐行往返、事件量有界；记录最坏 I/O           |
| 同时导入、打开图片、多个艺术家检测、领域重试       | 去重不因手动优先级持续挤占其他后台任务                       |
| 单个大视频、NAS 卡读、DB 断线、kill Worker、失租约 | 无继续发布或进程泄漏；仅完整文件缓存可复用；取消延迟如实报告 |
| 交叉清理计划、保留者删除、其他账户新建标记         | 数据库约束及写入口守卫阻止互删和整理数据竞态                 |
| 每个移动前后及 DB 提交前后崩溃、恢复路径占用       | 可解释恢复，不覆盖未知文件，不将半完成误报成功               |
| 隔离后保留者被替换、删除或损坏，URL 到期校验失败   | 不永久删除原内容最后一份，保留隔离件且保持可解释的恢复资格   |
| 附属文件、章节差异、多归档 revision、清理后重扫    | 未审内容保留，隔离不被重新导入，来源状态一致                 |

性能报告必须包含环境、样本、缓存冷热状态、候选率、stat 延迟与吞吐、实际读字节、哈希吞吐、峰值 RSS、数据库往返与写入量、每小时事件数，以及同时浏览和其他 writer 的延迟。暂停请求发现延迟与 reader 退出延迟分开记录，不能承诺立即取消。

第一阶段交付只读检测与审核时，完成缓存/并发/失败/大数据量验证；第二阶段在全部写入口协调、隔离恢复和保留者保护通过故障注入后开放清理。全量检查按[测试策略](../development/testing-strategy.md)执行；浏览器与手机视觉回归由用户执行。
