# WebP 手机播放调度与诊断

代码已实现；真实手机性能结论等待 Mate 40 Pro / HarmonyOS 4.1.2 实测。桌面模拟低刷新率不能替代手机验收。

## 播放行为

默认按媒体时间轴选择画面，消费过期帧而不绘制。Worker 仍按顺序解码和合成；省略显示不会省略动画依赖的合成。过期帧在 RAF 和 Worker 消息到达时归还额度，避免两帧队列把吞吐限制为绘制回调频率的两倍。首帧、循环边界及尚未确认后继的末帧仍绘制。末帧至少获得一次绘制机会，结束必须满足媒体时间轴终点及有效 EOF。

队列耗尽是真实缓冲：冻结时间轴，恢复后不追赶缓冲等待。暂停冻结剩余时间，同图继续复用实例；切图、重试和销毁隔离旧事件。`presentedMs` 与 `positionMs` 计入已消费但未绘制的媒体时间，不再表示所有帧都实际展示。元数据仍只是进度分母，不能推断 EOF。普通控制条不显示 loading，不增加缓冲提示。

本轮不修改原生 C/WASM、分辨率、两帧背压和内存预算，也不改写原图、增加数据库或服务端转码。解码吞吐不足仍可能缓冲，调度修正不承诺解决全部手机性能问题。

## 在手机上测量

1. 更新应用后，在已登录作品详情地址添加 `?webpDiagnostics=1`；已有查询参数时追加 `&webpDiagnostics=1`。刷新页面，打开问题 WebP 的弹窗。
2. 展开「WebP 性能诊断」。按顺序运行「旧调度」「新调度」「新调度 · 不绘制」，每组重复三次，共九份报告。每次等待结束后再开始下一次，保持前台、同一浏览器及相同手机设置。
3. 开始测试会停止原播放和自动浏览，独立播放一轮；完成不自动恢复或切图。「不绘制」保留静态海报，但仍解码、复制像素并传递消息。诊断运行不计入正常预览的有效观看。
4. 点击「复制报告」或「下载 JSON」。复制权限不足或下载调用失败时会显示可手动复制的文本框。报告仅在当前页面内存保留最近十次，刷新会丢失；切图或关弹窗中止当前测试但保留部分报告，切后台、手动停止、120 秒超时同样记录中止原因。
5. 一并记录手机型号、系统、浏览器名称和版本，并说明原图播放正常。首次运行与后续运行分开分析，重复运行不等于浏览器缓存命中。
6. 移除查询参数并刷新可关闭入口。诊断不上传，不改变登录权限，不提供任意 URL 输入。

## 报告格式与解释

导出形状为 `{ "version": 1, "results": [...] }`。每个结果包含 `outcome`、`setupMs`（清单/模块准备时间）、`testElapsedMs`（从点击开始至停止）及 `report`。清单加载阶段即被取消时 `report` 为 null。结果是独立匿名运行，不带媒体路径、标题、地址、ID 或凭据；浏览器 UA、视口、DPR、画布尺寸及资源构建版本用于比较环境。

以下为单次结果的**节选示例，数字为说明用途，不是手机测量结果**：

```json
{
  "outcome": "completed",
  "setupMs": 12,
  "testElapsedMs": 2050,
  "report": {
    "version": 1,
    "runId": "anonymous-run",
    "mode": "timeline",
    "resourceVersion": "build-version",
    "status": "ended",
    "elapsedMs": 2038,
    "firstFrameMs": 38,
    "playbackWallMs": 2000,
    "decodedMediaMs": 2000,
    "decodedFrames": 120,
    "drawnFrames": 61,
    "skippedFrames": 59,
    "pausedMs": 0,
    "bufferingMs": 0,
    "queueExhaustions": 0,
    "timings": {
      "draw": { "count": 61, "samples": 61, "totalMs": 61, "meanMs": 1, "p50Ms": 1, "p95Ms": 1, "maxMs": 1 }
    }
  }
}
```

`timings` 实际包括 `decode`（解码/合成尝试，包含待输入及 EOF 检查）、`copy`、`readWait`、`append`、`delivery`、`draw` 和 `raf`。每项累计次数、总耗时及最大值精确累积，分位数来自至多 4096 个样本的蓄水池抽样；不持久化逐帧轨迹。诊断默认关闭，不额外采样或发送统计消息。诊断本身有开销，三种模式均在相同测量条件下比较。独立测试不驱动正常播放的 React 进度更新和自动浏览，因此结果不能排除普通播放业务组件的额外主线程负载。

- `playbackWallMs` 从首帧到结束，包含暂停和缓冲；`decodedMediaMs` 是解码出的归一化帧时长之和，只有完整单轮完成才用作速度比值。
- `firstFrameMs` 从播放器 load 开始，不包含上层清单/模块准备；结合 `setupMs` 判断首次启动。
- `readWait` 是流读取等待，不等于纯网络耗时；`append` 包括追加及解析。`delivery` 使用两线程的 timeOrigin + now，比值包含消息排队，不等于纯传输时间。
- `draw` 只测 Canvas 调用，不包含完整 GPU 合成或屏幕呈现。关闭绘制前后的整体时间差比单独一个 draw 数字更有判断价值。
- `raf` 不跨暂停及真实缓冲采样，反映活跃绘制回调间隔，不是设备面板刷新率的直接测量。

## 验证与后续决策

可控时钟验证持续供帧的 2 秒/60fps 动画在 60、30、20Hz 下不超过两次回调误差；旧调度在 30Hz 下约 4 秒。真实浏览器验证 Worker/WASM 的流式、EOF、循环及跳过绘制后的局部/透明帧像素一致性。性能基准独立运行，不与构建并发。

手机每组取三次结果并保留首轮差异；无明显供帧不足时，播放墙钟时长目标为归一化时长的 110% 以内。先比较新旧调度，再比较新调度有/无绘制。若解码合成占主导，后续评估解码及原生替代；复制/绘制占主导则评估减少像素输出或按显示尺寸缩小分辨率。本轮不先承诺缩放收益。

回滚应用版本即可恢复旧调度，无数据迁移或原媒体恢复步骤。旧调度仅在显式诊断测试中保留，不是普通播放开关。
