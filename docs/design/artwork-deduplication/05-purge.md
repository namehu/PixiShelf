# 第五阶段：手动永久清理与交付

本文是尚未实现的开发规格，依赖[第四阶段](./04-isolation.md)及恢复演练完成。公共权限、图示、分工和阶段门槛见[总计划](../artwork-deduplication.md)。本阶段才开放 `purge`，没有按隔离时间、磁盘空间或定时任务自动清理的入口。

## 永久清理授权与执行

`purge` 接收 operationId、明确的隔离 itemIds 或该版本下全部隔离项、expectedVersion、expectedUserId、幂等键及对应版本的永久删除确认。服务端冻结最终范围、保留者和独立内容证据；不接受客户端路径、哈希或授权标志替代数据库证据。重复提交返回同一业务操作，过期确认要求重新查看，不能自动扩大到后来新增项。

1. 只接受完整 `ISOLATED` 项。处理中、部分失败或 `RECOVERY_REQUIRED` 项先修复，不能用 purge 作为忽略异常的手段。
2. 重新认领保留者和待清理副本，确认外部停写前提及备份检查点仍适用，协调 App/扫描/归档并等待有关执行 drain。
3. 绕过缓存完整读取保留者，核对原操作冻结的原媒体多重集合，而不是只检查作品存在或可以打开。保留者被替换、缺失、损坏、成员变化或失去有效状态时，停止清理并保持副本可恢复；本次不自动改选其他保留者。
4. 核对隔离文件的清单、当前位置和身份。隔离身份/属性变化或出现未知内容时停止，不猜测同名文件仍属于本操作。经审核的附属文件授权独立保留，不把媒体相同表述为所有附属内容也有副本。
5. 持久化清理意图后，按精确 manifest 逐项 unlink，记录“待删/已删”的可重放收据并同步必要目录；只有文件处理全部完成才删除业务对象。不能递归清理整个艺术家或隔离根。
6. 文件删除成功、数据库提交失败时，恢复只补做原冻结操作的数据库步骤；对已有清理意图且已确认先前身份的目标，重放发现文件缺失可确认已删除。若同路径出现不同身份文件则停止，不误删新文件。
7. 业务删除和来源 tombstone 提交成功后，操作项终结 `PURGED`，按已确认的终态释放声明；个人评分、阅读、单图标记按作品既有永久删除规则级联。独立操作证据和必要来源快照不随 Artwork 删除。

清理失败使用 `retryOperation` 继续持久的 PURGE 意图，复核原授权版本、保留者和文件现场；这与仅接受 ISOLATED 的新 `purge` 请求不同。原授权不再适用时保持待处理，不能自动扩展范围或以恢复按钮掩盖已删除文件。

清理开始后不能承诺恢复已删除文件。失败时明确列出已清理/未清理项，仍在隔离的未清理项保持保留约束；重试只访问原冻结范围。数据库 lease 失效、磁盘错误或执行不确定时停止推进，旧执行退出前不能启动替代清理进程。

URL 的人工授权绑定操作 ID、操作版本与执行关联。既有 PURGE_ARCHIVE 即使收到普通重试或到期触发，也必须验证 dedup hold 与专属授权；hold 保持到终态，不允许“先解除 hold，再调用通用 purge”的竞态窗口。

## 来源抑制、保留与查询

非 URL 作品清理时，把临时来源抑制转为持久 tombstone；身份使用受信根身份加已冻结来源身份/规范定位，不能只存可级联删除的 Artwork ID。扫描、审计发布、本地再导入及旧任务最终发布均检查该记录。不能依赖 Artwork 外键继续存在来阻止再导入。

显式重新导入是独立领域动作：管理员从隔离区历史详情查看已清理项并选择“允许重新导入”，服务端重核 tombstone 版本及来源身份，记录授权、推进导入代次后才允许新任务导入；旧任务绑定旧代次，即使 tombstone 已解除也不能重新发布。该动作只取消后续导入抑制，不恢复已永久删除文件，不接受任意路径；普通重扫、任务重试和根重新挂载不能自动清除 tombstone。新增 API 以 `artworkDedup.allowReimport` 表达这项明确操作，沿用账户、版本及幂等保护。

检测 run/item 默认 30 天清理，但活动 run、当前展示结果、审核/计划引用不参与 GC。清理计划、操作 manifest、恢复证据、未终结声明、来源 tombstone 与 URL hold 不随该保留期删除；本版不设置它们的自动过期。历史列表按批次/项目游标分页，避免长期保留造成单次查询无限增长。缓存 GC 只能清理派生记录，不能衍生出原文件删除任务。

## 升级、恢复与最终检查

正式 migration 采用新增表/索引及必要任务契约扩展，不扫描原媒体。验证空库完整 deploy 与有数据源版本升级，核对 `_prisma_migrations`、唯一约束、FK 和原数据保留；禁止 db:push。开工快照包含三 lane 下载改造，部署兼容性必须按这一基线核验。

部署顺序固定为：建立符合[备份基线](../../operations/backup-and-recovery.md)的一致性检查点，部署 migration，部署具备新类型与版本 capability 的 Worker，验证 READY/注册表，再开放 App 入口。旧 Worker 先退出，不让不理解新状态或 URL hold 的执行器消费队列。

回退时先关闭新操作入口并停止领取，确认执行进程退出。只读检测可保留派生缓存后回退兼容版本；已经存在隔离/清理操作时，必须完成在途恢复或保留兼容维护执行器和数据库结构。不能直接切换不识别 hold/tombstone 的旧镜像。人工恢复操作按 manifest 和完整备份处理，不用 SQL 把半完成状态改成成功。

最终执行主应用 lint、typecheck、test、build，受影响 DB/contracts/runtime/executors/Worker 检查，迁移及真实数据库集成测试，文档检查、图示生成/检查和应用路径大小写检查。迭代阶段只运行受影响检查，最终才统一全量；主应用 build 按工程规则使用必要权限。

性能交付使用 1,000 作品 × 平均 500 登记媒体的规模，分别记录少量候选、全部候选、冷缓存、热缓存、单文件变更和同时下载/浏览/发布。报告样本实际字节、候选率、属性延迟、读取吞吐、峰值 RSS、SQL/写入/WAL、事件量、任务等待、取消发现与 reader 退出延迟。真实 NAS 仅做有界只读测量；没有测得的存储吞吐、断电恢复或手机真机行为明确列为未覆盖，不能伪造通过。

先完成独立代码审查、修复复审，再由指定浏览器 agent 用可销毁样本统一验证 D1 至 D5 的全部浏览器案例，包含 D5-B01/B02。全量检查、图文设计一致性、每阶段证据和遗留限制汇总到发布记录；主 agent 重新核对主线变化后才准备合入。最终单独列出手机真机需确认的长按/触控、底部安全区、软键盘与浏览器差异，不把设备尺寸模拟等同真机通过。
