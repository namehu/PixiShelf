# 去重检索、性能日志与进度展示改造

本计划经用户确认，在新的 `codex/dedup-visual-search-v2` worktree 开发。基线为开工时最新 main `3a5b5ee26eec303378ed8b852379b033ef625420`。保留主目录、暂存区和其他功能分支；独立数据库、媒体、端口和 Worker 验证，验收提交后暂停，不自动合并或发布。当前行为仍以[功能规格](../../features/artwork-deduplication.md)为准，本页保留批准时的目标与契约，实际完成范围和限制见实施记录。

## 目标与执行顺序

借鉴 [Czkawka 的内存距离检索](https://docs.rs/czkawka_core/latest/src/czkawka_core/tools/similar_images/core.rs.html)及 [dupeGuru 的分块特征加载](https://github.com/arsenetar/dupeguru/blob/master/core/pe/matchblock.py)，同时更换候选索引和执行方式，不引入新搜索服务或重做删除流程。每次 10,000 个登记原件的生产上限不变，50 万规模另行验证。

1. 持久化方案与生产基线，固定日志口径，修复三处进度。
2. 内存两通道检索、关系复用、批量提交、校验去重及调度调整。
3. 同样本性能对照、安全及恢复回归、桌面完整流程、独立审查、文档与提交。

复杂算法和续跑逻辑由 Astra / high 实施；其他实施和独立审查由不同的 GPT-6.1 Sol / xhigh 承担；浏览器由 GPT-6.1 Sol / medium 验证。只跑受影响专项、类型检查、必要构建与文档检查，不重复全量验证。

## 检索与缓存

流程：文件与缓存核对 → 每页 500 条加载必要特征 → 内存检索 → 图片精比 → 批量提交 → 作品配对与发布。

- 整图通道：完整感知哈希 BK-tree 范围查询，距离不超过 12。
- 局部通道：同一对视图至少 7 个有效局部区域距离不超过 10，且整图距离不超过 28；两通道取并集。
- 沿用有效信息量、长宽比、白边和裁剪约束；不能合并不同视图的零散区域投票。
- 同作品和反向重复对提前排除，多视图候选按图片对去重；边界统一校验、哈希转换数值后内部类型化流转。
- SHA 精确配对优先，保留文件重复次数、一对一配对、未配对页及动图未核对状态。
- 特征版本与检索版本分离：新索引不使有效原特征失效；新算法不继承旧算法的完整无匹配结论。
- 新算法静图范围完整覆盖且输入未变时直接复用关系，跳过索引和候选遍历；新增或变化作品仅重算涉及它们的关系（包括与未变作品的关系）。
- 动图未核对与静图未完成分开，失败、中断、预算截断不能作为完整负结果；FULL 绕过缓存。
- 新旧结果允许不同，但以小样本穷举精比 oracle 核对检索完整性，独立标注样本判断误配/漏检并解释差异；密集样本记录树节点访问量，不假定 BK-tree 永远高效。

## 执行与安全

- 单计算线程，初始特征和索引预算 128 MiB；超限明确报告，不丢候选。单批最多 128 张查询图、2,000 次精比或约 1 秒计算，先到收口，单查询可跨批。
- 新引擎不再写逐运行 posting，旧表和旧执行器保留。普通特征读取移出写事务围栏；提交时一次批量检查执行权、源、成员、根/目录与写入声明，消除同事务重复检查。
- 只缓存冻结输入，不缓存安全判断。结果、游标和计数原子提交；失租约零提交；重启重做至多最后一个未提交批次。发布校验及实际删除前完整读取不削弱。
- 纯计算阶段不每片启动文件读取子进程；约 10 秒释放 writer lane，纯计算阶段无固定 3 秒冷却，重新参与原调度。读取阶段节流保留。
- 计算阶段的立即让行使用明确的 scheduling yield 语义：队列提交时将已到期的可执行时间收敛至提交时刻，不因构造时间与事务提交相差毫秒而回滚，也不增加固定冷却。未来的可执行时间保持不变，scheduling yield 必须保留 attempt；普通失败重试仍遵守原有时间和退避约束。
- 短暂让行可复用只读索引但不能复用执行许可；暂停、输入变化、任务切换或 Worker 重启释放/重建。后置读进程清理失败及最终发布失败也要释放索引，不能让同 run 的重试沿用失败尝试缓存。
- 新扫描协议和检查点版本只用于新任务；旧活动任务按旧协议续跑。加法迁移不扫描媒体、不重写历史结果或删除授权。
- 遵循最新 AGENTS.md：边界校验一次，不新增无必要的抽象、重复 try/catch 或理论防御层。

## 统一进度契约

增加版本化 `kind: artwork-dedup` 的 `progressData`，字段至少含阶段、阶段完成量/总量（未知为 null）、单位、等待原因、采集时间。`getRun`、任务中心、任务详情和检查页使用同一持久快照。内部 UI 不能再用原件/作品阶段完成度推导整体 99%。

- 核对原件/准备特征显示阶段及已处理量；视觉查询显示“正在比较图片 · 2,702 / 5,624”。
- 配对/保存阶段总量未知时显示不确定进度；如有百分比，只表示当前阶段。首版不估算总 ETA。
- 自动让行显示“等待后台调度，将自动继续”；用户暂停与本轮上限等待明确区分。
- 仅最终发布成功可表示任务结束；存在未核对媒体明确说明，不把它们当已匹配。
- 查询完成数只计完整处理的图片，不用 ID 或比较次数代替；计数与游标同提交，续跑不重复累计。
- 总量为零/未知不除法；旧记录无结构化进度时显示可知阶段，隐藏误导性的旧数字。
- 不为轮询新增全表 COUNT；复用现有推送/轮询，进度写入复用检查点。

## 性能日志契约

复用 Worker JSON logger、SystemJobEvent 和运行记录，加可空性能汇总；每 30 秒及阶段切换/暂停/失败/完成输出，不逐图或逐候选发事件。持久汇总随现有检查点更新。

| 类别      | 必须包含                                                          |
| --------- | ----------------------------------------------------------------- |
| 关联      | runId、jobId、协议/检索版本、输入摘要、批次、采集截止时间和完整性 |
| 进度      | 原件、静图、未核对、阶段总量和完成量                              |
| 文件/缓存 | 读取字节、解码数、自身/同内容特征命中、关系复用和失效原因         |
| 检索/精比 | 索引构建耗时、节点访问、通道命中、去重候选、实际精比和配对耗时    |
| 数据库    | 加载/校验/写入调用次数及耗时、事务数和总耗时                      |
| 调度/资源 | 活跃、排队、冷却、暂停耗时、内存峰值、重建次数和重放工作量        |

索引访问、精比、DB 调用分别计数；DB 调用不冒充 SQL，精确 SQL 由隔离专用客户端统计。事务 wall 包含往返/等待，不称 WAL 时间。重放与已提交计数分开，缺失不记零；不记录原图、绝对媒体路径、SQL 参数或连接秘密。

交付两个 DBX 只读模板：单 run 瓶颈和双 run 对比。先核对输入/版本/缓存条件，缺失指标说明未知，全实例统计不归因给单任务。

## 验收门槛与追踪

| 需求/流程                   | 实施      | 验证与证据                                                             |
| --------------------------- | --------- | ---------------------------------------------------------------------- |
| 两通道候选→精比→作品关系    | 第二批    | 穷举 oracle、遮挡/压缩/白边/裁剪/重复页/公共封面/负对照，解释新旧差异  |
| 混合媒体→图片对照→确认→删除 | 第二/三批 | 静图参与、动图未核对、仅隔离合成样本实际删除                           |
| 热复用/少量新增             | 第二/三批 | 同输入摘要冷/热、增量关系无漏检、热检零解码/零候选遍历                 |
| 检查点→暂停/取消/重启       | 第二/三批 | 连续与重放结果一致、失租约/源目录变化/事务失败零过期发布               |
| 真实阶段进度→三个页面       | 第一/三批 | 原件完成但视觉一半不得报99%，自动/人工等待、0/null、旧记录、刷新与重启 |
| 性能指标→DBX查询            | 第一/三批 | 统计去重/缺失/脱敏；同样本同硬件，旧/新日志可复核                      |

目标（未达到不可宣称通过）：特征就绪后的检索与配对耗时至少降低 80%，同阶段事务至少降低 90%；完整热缓存不解码、不遍历候选；纯计算无固定冷却；同时报告内存和并发浏览响应。旧生产半程观测不作为完整 A/B 基准。检查与测量结果写入[本轮记录](../../records/artwork-deduplication-visual-search-v2-2026-10-29.md)，发布后再用日志验证生产效果。
