# 作品去重：包含关系与相似版本扩展草案

用户已于 2026-10-25 批准实施第一批完整包含；第二批视觉识别仍为草案。沿用[已实现流程](../../features/artwork-deduplication.md)的后台任务、四来源、检查页面、确认与原地删除；增加两种识别能力，不重新建设维护系统。视觉实现前仍需用图片样本确定感知指纹阈值、检索参数和资源上限，本草案不宣称识别率或生产吞吐已经验证。

## 1. 用户能得到什么

仍从艺术家页点击“检查重复”。默认检查完全相同、包含关系及相似版本，首次需要补建图片指纹，后续复用。四种来源及混合来源均适用，前提是作品归属到同一个艺术家；不会按 Pixiv/E-Hentai 名字猜测创作者或无码状态。

| 结果         | 展示示例                                                               | 处理原则                                         |
| ------------ | ---------------------------------------------------------------------- | ------------------------------------------------ |
| 完全相同     | 两部各 80 张，原文件全部一致                                           | 保持现有重复组与推荐规则                         |
| 完整包含     | A 的 80 张全部在 B 中，B 另有 20 张                                    | 推荐保留 B；有整理记录冲突时明确展示，不自动合并 |
| 疑似不同版本 | 80 张画面对应，其中 65 张原文件相同、15 张画面相近；B 另有 20 张未配对 | 并排核对不同的图片，由用户选版本，不默认勾选删除 |

部分重叠也不冒充完整包含：若 A、B 各有 100 张，只匹配 80 张，说明“两边各有 20 张未匹配”。相似页的“未匹配”不能称为确定独有；只有完整的字节比对才能证明原文件没有出现在对方中。

照片、漫画静态图片是本次视觉识别范围；原文件精确比对仍覆盖动画和视频的全部登记原件。动画、视频不能凭封面推断整段相似；混合作品须列明未做视觉检查的媒体，不能显示整部已覆盖。

## 2. 完整包含：复用 SHA-256，改变作品之间的比较方法

扩展前的 `buildArtworkDedupCandidates` 要求整部大小清单相同；第一批移除包含分支的这一限制，避免 80 张与 100 张在入口就被排除。

1. 冻结本次作品范围、检查文件属性，复用有效的逐文件 SHA-256，补算缺失或失效项。旧算法只对候选算过哈希，不能假设图库已经全量有缓存。完整作品指纹继续按原算法产生，供快照与删除复核使用。
2. 将每部作品表示为 `(大小, SHA-256) → 出现次数`。若 A 的每一种文件在 B 中都有足够次数，才判定 A 被 B 完整包含。文件名、排列顺序不参与；重复页的次数参与。
3. 使用现有 `(size, sha256, imageId)` 索引建立限定在本艺术家快照中的“文件指纹 → 作品”查询。先从 A 中最少见的文件取得候选，再核对全部计数；不用每张图片与其他所有图片比较。可靠大小计数可提前排除不可能包含的作品，但不能再要求整套相等。
4. 完全相同的作品先归组，再比较组代表，减少相同内容反复参加计算。高频公共封面不能直接产生海量图片配对；保留聚合的作品及次数，分批验证候选。

80/100 的例子最终是 A 覆盖率 100%、B 覆盖率 80%，保留 B 才覆盖全部原媒体。缺失、不可读、变化中的文件记为未完成，不用减少分母的方法伪造 100%。

## 3. 有码与无码：比较画面结构，再汇总对应页

建议先用轻量感知哈希，不引入大模型、GPU 或向量数据库。执行器已经依赖 `sharp`，可以复用现有图片解码能力，哈希算法采用经过样本核验的 DCT pHash 实现。

**图片特征。** 在受控子进程内读取当前原图，统一 EXIF 朝向、色彩和透明背景，缩小后生成一份整图指纹及九宫格的局部指纹，同时记录宽高比、各区域的信息量和算法版本。具体网格与阈值是小样本验证参数，不做用户配置面板。

**为什么有机会匹配有码版。** 局部遮挡会改变局部画面；其余区域的构图和线条往往仍对应。整图指纹先寻找相近页，局部指纹补充整图漏掉的候选，再核对多个有信息的区域是否一致、差异是否集中在局部。白边、纯色块、统一水印不能独自作为匹配证据。该方法是本项目的候选设计，不能预先承诺所有遮挡方式均可识别。

**从图片到作品。** 先匹配 SHA 完全一致的页，再对剩余页做视觉匹配；同一张页不能反复充当多张页的对应项。候选作品之间建立一对一配对，存在歧义就保留待核对。用双方已配对页数/各自总页数、原文件一致数、视觉相近数、未配对数描述结果，不用一个“相似度 95%”掩盖缺页。

**候选检索。** 将整图和局部二进制指纹分段建立多组桶索引，命中后再算完整距离和局部一致性，避免遍历全部指纹。一次处理本艺术家的一种视图，复用紧凑数组和工作缓冲区；数据库保存指纹，检索索引可按任务重建，不部署独立搜索服务。近似检索可能漏召回，桶参数必须用样本测量；不能宣称“没有建议”等于“绝无相似作品”。

**作品门槛。** 较短作品的大部分页能对应且有多张不同画面的证据时优先展示；初始可试用较短作品 80% 的配对比例作为排序/展示阈值，最终由样本确定。单张或极短作品另按强单页证据展示，不能因不足多页而永远查不到。统一封面、模板相似或同一人物不够；少量重叠可作为次级结果，不默认进入删除选择。

**能力边界。** 它识别“疑似同一作品的不同版本”，不自动认定哪部无码，也不按站点推荐版本。重度遮挡、大裁剪、拼页、翻译改字和大量差分可能漏检或混淆；展示实际对应页和未配对页，由用户决定。首轮必须包含这些反例，不能只用轻度压缩图校准。

算法依据：[pHash 的 DCT 设计](https://www.phash.org/docs/design.html)支持对轻度模糊、压缩等变化进行结构匹配，并不提供语义理解；[OpenCV 图像哈希模块](https://docs.opencv.org/4.13.0/d4/d93/group__img__hash.html)列有 pHash 和分块算法。九宫格组合及漫画版本识别效果仍须本项目验证，不直接采用这些文档中的通用阈值。

## 4. 缓存与 50 万张图片

复用现有 `MediaContentFingerprint`、`ArtworkContentFingerprint`、源代次、租约和失效协议。新增视觉指纹缓存，绑定原媒体身份/内容 SHA、源版本、算法版本和规范化参数；不能把旧缩略图或失效哈希当成当前原件证据。相同字节的文件可共享已验证的视觉计算结果，但每个路径仍各自核对身份。

| 变化                   | 需要做的工作                                                               |
| ---------------------- | -------------------------------------------------------------------------- |
| 首次扩展检查           | 补齐选定艺术家的 SHA 缓存，并为静态图片建立视觉指纹；不在迁移中扫描图库    |
| 第二次，无内容变化     | 核对属性，复用 SHA、视觉指纹和版本匹配的作品关系；不重新读原图内容来算特征 |
| 新增作品或修改部分图片 | 补算新增/失效文件，更新涉及这些作品的关系；与已有作品用缓存比对            |
| 改名、标题或重排       | 不因展示变化重算画面特征；定位使用媒体 ID，显示序号重新解析                |
| 调整匹配阈值           | 使用现有视觉指纹重新匹配，无须重读图片                                     |
| 特征算法或规范化改变   | 仅视觉缓存按版本重建；有效 SHA 无须随之全部重算                            |
| 用户要求完整检查       | 对所选范围绕过相应内容缓存；删除前仍按现有规则完整读取已选择的作品         |

50 万张的全图片两两比较约 1250 亿对，明确禁止采用。仍按艺术家执行，即使单个艺术家有 1000 部 × 500 张，也先用倒排/桶检索产生候选，再在候选作品内部配对。工作量取决于图片数、索引命中数和候选数，不能把高频桶最坏情况宣称成严格线性。

- **冷缓存成本不能消失。** 若平均每张 2 MB，50 万张约 1 TB 原始内容，首次哈希/解码至少需要访问这些内容；解码器可能额外读取，按实际计数报告，不承诺一次磁盘读完成或几分钟跑完。仅查选定艺术家，后台可暂停续跑。
- **特征体积可控。** 若采用 1+9 个 64 位哈希，50 万张的哈希净载荷约 40 MB；这不是数据库、索引或进程总内存。实现使用二进制存储与分批索引，数据库行/索引和解码峰值另外实测，不把所有原图或 JS 对象常驻内存。
- **沿用现有调度。** 媒体分页 500、属性并发 4、内容读取并发 1、缓存批次 100、约 10 秒/256 MiB 文件边界让行并冷却 3 秒。视觉解码默认并发 1，另限制输入像素、单图处理时长和子进程内存；超过上限标为未完成，可继续其他项目，不能按“不重复”处理。
- **控制高频候选。** 低信息区域不独立投票，相同指纹合并保存出现位置；不在数据库持久化所有未命中的图片对。高频桶、候选和配对处理有预算与检查点，超预算明确保留待处理，不能静默截断后显示检查完成。
- **热缓存仍有成本。** 属性检查、数据库查询和索引重建仍需时间；批量读取有效性、合并同阶段重复 inspect、减少逐文件事务是本次必做的热路径调整，删除前的独立复核不省略。

[现有 50 万规模记录](../../records/artwork-deduplication-phase-2-performance-2026-10-23.md)采用 50 万登记媒体、少量共享小文件，未做视觉解码；热轮内容读取虽为零，属性/数据库处理仍有明显耗时。它不能证明 50 万独立图片、NAS 或新算法的吞吐。

新增验证拆开做：50 万条特征验证数据库、索引与高频候选；有代表性的独立图片验证读取/解码与识别；再做一次组合验证。使用实际图片测到吞吐后才能给完整图库估时。记录内容读取字节、解码数、两种缓存命中、候选量、峰值内存、数据库语句/写入及同时浏览下载的延迟；不逐阶段重复跑全量构建。

## 5. 页面和删除如何衔接

保留现在紧凑的检查结果、确认侧栏和删除记录，只增加关系标签及一句解释。结果默认优先列完全相同和完整包含，相似版本显示“查看差异”，不默认批量选中。详情提供“画面不同”和“未配对”筛选，桌面并排、手机可切换同一对图片；不重新堆缩略图墙、工程指标或新向导。

现有 `ArtworkDedupGroupMember` 限制每个作品在一次检查中只属于一个等价组，不能直接承载包含/相似关系。保留旧精确组，增加按作品对保存的关系与按需分页的页配对证据。A 像 B、B 像 C，不能推导 A 像 C，也不能把三者自动组成可删组。

沿用既有删除执行器，但入口与冻结证据必须区分理由：

- 完全相同：维持原规则。
- 完整包含：重新验证被删作品的全部原文件都在所选保留作品中，次数足够；默认只推荐删除被包含的一方。若用户反选导致有原文件未保留，必须转为明确的人工舍弃版本确认，不能沿用完整保留承诺。
- 相似版本：用户明确选择要舍弃的版本；确认中说明原文件并不完全一致、未配对页及整理记录会一并删除，不宣称内容无损。沿用一次永久删除确认，不叠加多级弹窗，也不自动合并两部作品。

原始 SHA 仍用于锁定用户实际确认的内容。冻结关系种类、配对证据版本、保留/删除作品及文件范围摘要；删除前完整重读参与作品，确认各自内容仍与确认时一致。对相似版本不要求两部 SHA 相等，也不能通过跳过各自快照校验实现放行。文件或关系变化则重做预览；同一批次中某作品同时被保留和删除须拒绝冲突选择。原有写保护、逐文件回执、来源抑制和重试范围继续使用。

## 6. 收敛后的推进顺序

只分两批，不重开原来的五阶段工程。

1. **包含关系闭环。** SHA 缓存补齐与候选筛选、方向/次数判定、关系结果、保留推荐、删除复核接入；同时收紧热缓存的重复属性查询和数据库往返。验收 80/100、80/100 改序改名、重复页次数不同、两边都有独有内容、混合来源、修改一张后的增量检查，以及冲突删除选择。
2. **相似版本闭环。** 先用一组本地授权的有码/无码、压缩、差分和不同作品样本验证整图+局部指纹。确认有效后接入持久缓存、候选检索、页配对与差异视图，再完成 50 万特征压力和代表性图片 I/O 验证。若小样本效果不足，停在算法选择处修正，不先建完整 UI 后再返工。

验收将“找不到目标”“把不同作品配在一起”“页配对有误”分别统计；阈值在调参样本确定后，用未参与调参的样本核验。有码/无码又有 80/100 页数差异的组合场景必须覆盖，不能只分别验证两种能力。缓存第二轮在文件未变时应无特征内容重读（打开预览及删除复核除外）；失效、取消、解码失败不得发布完整关系。

延续既定分工：只有匹配核心、缓存一致性和删除证据衔接等复杂实现用 Astra / high；普通实现及独立审查用 GPT-6.1 Sol / xhigh；最终浏览器用 GPT-6.1 Sol / medium。每批只做相关测试与独立差异审查；批次末验证桌面/手机的检查、确认与删除流程，完成后收口暂停。

## 7. 第一批固定契约

第一批只开放完整包含的安全方向：保留完整者，删除被包含者。反向选择不进入本批删除；上文人工舍弃版本的确认属于第二批，不通过取消覆盖校验来提前开放。

- 沿用 `listGroups` 的结果 ID、成员分页、`saveReview` 与 `prepareCleanup` 入口。结果增加 `relationKind: EXACT | CONTAINS`；包含结果提供 `containedArtworkId`、`containerArtworkId`、`containedFileCount`、`containerFileCount`、`extraFileCount`。计数仍为十进制字符串，精确组对应的包含字段为空。
- 新增独立作品对关系记录，保留精确组及其成员唯一键。包含结果固定两部作品；多个关系可以涉及同一作品，不做相似链式归组。
- 被包含者有任一账户的手工整理记录时，要求显式选择完整者后才能处理；UI 沿用私人记录隔离，不透露其他账户的具体标记。
- 确认快照冻结关系类型与方向。跨结果共同保留的作品只冻结一次；同作品既保留又删除、或被多个选择重复删除时拒绝该选择，不能在确认时悄悄缩小范围。
- 旧 Worker 不得按旧精确语义执行新包含操作，沿用既有任务/操作版本门禁保守处理。新 Worker/迁移只部署到本批隔离环境，用户服务升级另行操作。
- 包含操作冻结 `protocolVersion=2`，维护任务使用新的 `definitionVersion=3`，旧执行器拒绝消费；既有精确操作仍按协议 1 处理。确认使用服务端返回的协议版本，不能在页面写死为 1；范围摘要绑定包含方向与协议，不能复用旧确认授权。
- 新检查使用扫描任务版本 2，入口要求 READY Worker 声明该能力；旧扫描版本 1 的结果通过 `includesContainment=false` 标明仅检查完全相同，不能展示成已排除包含关系。Worker 保留旧任务版本处理能力。
- 数据库升级覆盖非空旧库与空库正式迁移，删除验证只用独立合成媒体，恢复依据为可重建的样本清单；不操作真实图库，不重复跑全量 App 验证。
