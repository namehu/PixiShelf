## 实验安排

保留规模库开工时约有 1,660 万条 posting、大小 3,930,657,583 B，`n_mod_since_analyze=0`；人工 analyze 计数仍为第五批留下的 1。复用原 5,000 条特征及 Image ID，不生成 100,000 条新样本。历史 probe 的完整结果和输入摘要先固化，再仅把已完成且无进程的合成记录 `3866f090-058c-4b04-af61-e16f9a9dc633` 从 `RUNNING` 收口为 `COMPLETED`，不修改原计数或证据。

新增一份 `CANCELLED` 合成运行只作为旧／新 SQL 只读对照载体，不声称它执行过完整业务检测；另建完整冷／热运行。每份约 200,000 posting，三个运行约增加 600,000 行。每阶段保存新 run 是否进入 MCV、统计时间和自动分析计数，禁止刷新统计使优化结果显得更好。旧完整任务及 100,000 特征测量不重跑。

生产实现前先在独立小库验证 SQL 形状：历史 fixture 建统计后，在事务内插入尚未统计的新 run。旧查询仅按 runId 定位后过滤 key；简化 `LATERAL` 查询能以 runId／key 双等值索引定位，并通过外层 `LIMIT` 按需读取，不需要递归查询或新增数据库对象。小库 fixture 的一次统计用于复现测试前提，不进入产品或保留规模库操作。

## 实现与定向检查

`candidate-postings.ts` 将最多 160 个去重特征键作为有界输入，用一条 SQL 逐键执行 runId／key 等值索引查找。内层与外层均受 20,001 行上限约束，无外层排序。未到上限时返回全部 posting；到达上限时正 multiplicity 保证现有预算判断拒绝该查询。只返回消费所需的 imageId／multiplicity，候选图片仍按数值排序。`visual-batches.ts` 只替换原读取事务中的一次查询，其余安全围栏、合法前缀、比较／提交、持久检查点和生产预算不变。

专属 `f03_candidate_postings_20261028@55432` 从空库正式部署 126 项迁移。一次名称筛选执行 20 项通过、20 项未选中（不计通过）：包含 7 项新查询专项及 13 项已有分批用例，覆盖最后 key、重复 key、同图跨 key 权重、20,000／20,001 行、权重先于行数超额、旧统计、取消／执行权／来源变化、合法前缀与恢复不重查。EXPLAIN 在密集首桶及跨桶两种分布中实际总索引输出均为 20,001，分别只消费 1／3 个 key，没有 Sort。一次执行器 typecheck 通过。

测试库 14 类 fixture 表已清空、其他会话为零，保留迁移结构；生产源码冻结后才移交规模测量。独立审查确认此轮未改变页面、API、删除授权或部署协议，无需重做第五批桌面流程；本批验收以数据库结果、执行计划、续跑和构建为依据，不新增浏览器通过声明。

测量 harness 后续增加专用 SQL 对照入口，因此在最终冻结后另跑一次执行器 typecheck（不是重复检查未变源码），以及一次执行器／Worker 定向 build，均通过。没有运行全量 App lint、test、build 或全 Worker 链测试。Worker 构建保留三项既有 `import.meta`／CJS warning；`dist/main.cjs` SHA-256 为 `e392ae0ce7eb43b42e9df8f5fbbb8a10970082e855c752cbea77a753b4889575`。所有构建在计时开始前结束。
