## 视觉覆盖与重复开销

2,281 / 7,905 个媒体标为 UNCHECKED，占 28.86%，涉及 47 / 53 部作品。READY 与 UNCHECKED 的作品数可以重叠。5,624 个 READY 媒体表示特征可用，不能推算新解码或特征缓存命中次数。

当前 `indexArtwork` 只为没有任何非 READY 媒体的作品建立视觉索引，`artworkPages` 也拒绝含不完整媒体的整部作品。按本次记录和这段实现，47 部会被排除，最多 6 部进入后续视觉匹配。这不会否定已完成的 SHA / 包含关系，但不能将 0 个视觉结果解释为 53 部均无疑似版本。

特征准备发生在上述作品级排除之前，因此可能先为后来整部排除的作品准备部分特征。本次有多少读取/解码最终没有参与匹配，未采集，不能以 READY 行数推算。

实测部署版本的关系缓存选择要求历史 run 的视觉状态为 COMPLETE。首轮 INCOMPLETE 不能为第二轮提供视觉关系复用，符合两轮均实际比较 185 次、复用 0 次的记录。成功特征缓存与关系缓存是不同层；第二轮已提交读取为 0，不代表没有读取。

执行收口将读取进程报告字节减去本次已提交读取增量的正差计入 `retryReadBytes`。这里的“未提交”是读过但没有形成已提交的成功检查成果，不是数据库事务提交失败，也不等于文件被修改或用户执行重试。两轮该值精确相同，说明这部分记录开销没有降低。后续文件诊断确认了重复触发的确定性多帧排除原因，见下文。

`UNSUPPORTED_MEDIA` 同时覆盖视频/动画、超大小限制，以及部分读取或解码失败。现有持久结果不足以区分全部底层原因。按当前媒体类型/尺寸可以进一步分类，但当前元数据不能替代原运行时错误。

## 删除预览失败

确切操作为 `21007a97-1e13-4120-a3ee-370f47d09702`，关联第二轮；任务为 `63acbc4b-8674-4b62-9bf9-d30faf00b817`。首次诊断错误地将它限制在第一轮 run 下，得到空结果；之后用用户 URL 中明确的 operationId/runId 纠正，命中恰好一条。

- 创建 22:55:39.018，开始 22:55:39.973，任务结束 22:58:06.810；创建至任务结束 147.792 秒，初始等待 0.955 秒，开始后 146.837 秒。
- `mode=PREPARE`，`preparePurpose=DIRECT_DELETE`，协议 2；操作 `FAILED / DONE`，错误 `INVENTORY_BLOCKED`。调度任务 `COMPLETED` 表示核验流程结束，不表示预览通过。
- 保留 16831、16835，拟删除 18462、18465；两条包含关系分别为 170→174、200→203 个媒体。
- 共检查 751 个文件：747 个 MEDIA 核验和归属均通过；4 个 SOURCE_FILE 归属通过，但检查失败，`blockReason=FILE_CHANGED`，登记大小合计 546,772 字节。
- 四部作品的 inventory/inspection 游标均完成，作品级 errorCode 为空；分组 blockedGroups=0 不代表文件层无阻断。
- `directDeleteConfirmedAt=null`、`deleteStartedAt=null`、`deletedFiles=0`，且仍为 PREPARE：这次操作停在预览，未开始执行删除。
- 事件包含 10 次自动让行，对应下一次领取的间隔合计 31.114 秒。protocolVersion=2 的媒体预览路径没有协议 3/4 的逐媒体全文重读分支，不能将这 147.792 秒归因为重新哈希全部图片。

`completeArtworkDedupPrepare` 会因文件级阻断返回 FAILED/INVENTORY_BLOCKED；它没有发生任务抛错，因此 job_status 可为 COMPLETED。UI 将该预览失败显示为“删除未完成”，容易误导用户。

4 个阻断文件均为 `ARCHIVE_REVISION_REFERENCE`，对应归档版本清单（manifest），分别关联四部作品；并非 747 个已通过核验的媒体原件。登记大小分别为 126,720、147,358、126,393、146,301 字节，均没有保存 SHA 证据，但有 mtime、ctime、device、inode 属性。属性存在不表示内容成功读取过；后续目录检查可以记录这些属性。

追加诊断用部署 bundle 的来源清单读取器，在原 Worker UID 下核对四份文件：全部通过，属性与失败操作记录一致，清单身份有效，媒体数分别为 174、203、170、200。数据库显示它们都来自已完成的旧归档发布，唯一当前修订及导入项／图片／扫描哈希和大小对应关系有效，但 `sealedManifestSha256`、`generationToken` 及 generation 记录均不存在。

实际根因是清单证据函数只接受新封存机制，先报 `ARCHIVE_MANIFEST_UNVERIFIED`。准备流程捕获该错误时丢掉已读属性和哈希，后续目录检查再把空属性基线与真实文件比较，将原因覆盖成 `FILE_CHANGED`。因此这次错误不能解释成用户真的改了四个清单。限定时间窗的 Worker 日志只有任务领取／收口，没有保存更细的原始错误；根因由部署代码、文件复现与数据库证据共同核对。

最后追加只读核对完整清单 tuple 签名（真实页码、路径、SHA、大小）：四部作品分别 174／203／170／200 个成员全部与数据库导入项匹配。该核对覆盖本地新增的旧归档映射条件；它没有创建预览、认领维护任务或执行删除。

通过三项任务最后一个含 workerId 的事件关联 Worker，三条结果均为 `serviceVersion=latest`、当前 READY，启动时间均为北京时间 18:10:48.995，最近心跳为 23:27:48.465。没有看到重启迹象；该查询只核对各任务最后一次关联的实例信息，不等于审计完整进程史。
