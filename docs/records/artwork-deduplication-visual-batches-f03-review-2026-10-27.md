# F03 第一批独立审查记录

日期：2026-10-27。适用分支：`codex/dedup-visual-batches-f03`；比较基线：`261993af`。审查对象是独立 worktree 的未提交改动，包含新增但尚未跟踪的实现、迁移、测试和契约文件。审查者未参与生产代码实施，未操作真实数据库、媒体或用户进程，未重复运行全量检查。

## 当前结论

最终生产代码、两项 P2 修复、后续批量守卫热点修复及长测门禁已完成独立审查，当前未发现未修复的 P1/P2。第一批的持久分段、原范围恢复、兼容与有界装载目标有代码和隔离验证证据支持；原件、视觉匹配和删除授权边界保持。

10,000／10,001 预制特征内核均完成，但各需约 8 分钟、约 50 万条 SQL；这证明本批正确性与装载边界，不代表大图库性能达标。桌面验收和交付由统筹记录另行收口，本记录不表示生产部署或整个 F03 已完成。

契约预审另发现“失败重做查询”与每 50 候选检查点的表述可能冲突；契约已明确查询游标、查询内候选游标及未提交块恢复。实现还将最多 2,000 个候选 ID 存入检查点，已提交前缀恢复时不重新读取全部 posting。

规模测量另暴露逐作品守卫的数据库往返热点。新增 `assertArtworkDedupVisualItems` 限制最多 51 个合法作品 ID，缺 item／Artwork 或不满足可见性、有效艺术家归属时失败；`frozenMediaRevision`、快照字段非空、源 revision／epoch 和 writeToken 校验与旧逐项路径一致，并明确要求 item COMPLETE。`memberCount` 与旧路径一样依赖源 revision 守卫而不重复全量计数。调用仍先取得目录／根守卫，再按 ID 顺序锁住全部 Artwork；锁保留至检查点提交，最终发布守卫未替换。该修改已独立复审并通过受影响的定向回归。

## 规模计量复核

每部作品最多 1,000 页，每页预制 1 个完整视图、10 个信息区域、40 个 posting。10,001 档只通过测试内部 `fileLimit` 接缝放宽该次内核输入，公共入口仍保持 10,000 上限。计时从 fixture 与旧匹配器准备完成后开始，到 `scanBatchedVisualVersions` 返回结束；不含样本准备、测试收尾和完整 Worker 调度。

| 内核耗时                       |                                    487,253 ms |                         461,444 ms |
| SQL 事件／写语句               |                               501,013／70,503 |                    501,126／70,530 |
| BEGIN 事务数                   |                                        50,039 |                             50,046 |
| 实际比较                       |                                        27,532 |                             27,536 |

| heap 起点／采样峰值            |                 86,815,256／148,859,776 bytes |       52,109,304／66,034,480 bytes |
| 原媒体读取／视觉解码调用       |                                    0 bytes／0 |                         0 bytes／0 |

已核对测试计量代理每 fixture 只创建一次，观察 `ArtworkDedupMedia.findMany` 的实际返回条数，转发原参数和结果；SQL 观察器统计执行期间的语句、写操作和 BEGIN。heap 每 20ms 采样且包含 fixture 上下文，不是严格分配量；303,202,304 bytes 的 max RSS 是两档共用进程的累计高水位，包含计时前样本与旧引擎准备，不能当作每档独立峰值，也不能比较两档内存高低来推断算法趋势。

两个长测现仅在 `QUEUE_KERNEL_TEST_DATABASE_URL` 存在且 `ARTWORK_DEDUP_VISUAL_SCALE_EXCLUSIVE=1` 时运行；该开关只控制这两项测试的执行，不改变测量体、生产预算或普通 PostgreSQL 套件。已完成测量未因增加开关而重复执行。

小范围热点定位使用独立普通 PrismaClient，无上述计量代理：相邻同分布 20 个 QUERY 块由 1,928 条 SQL／1,361ms 变为 1,240 条 SQL／1,020ms，数据库执行时间为 160ms／199ms。两次不是严格同输入 A/B；初次未完成规模轮还包含每事务重建计量代理的额外成本，均不能推导固定产品加速比。

## 限制与覆盖边界

- 预制特征内核不代表真实解码、完整 Worker 吞吐或 NAS 性能。当前约 50 万条 SQL／档说明数据库往返仍是明显成本；下一批应先减少有界事务与重复查询成本，再推进 10 万／50 万，不直接提高文件或比较预算。
- QUERY 的取消、执行版本变化、源变化，以及 PUBLISH 的真实 lease 过期和目录变化已动态验证；PAIR 阶段逐项故障、根身份／写入声明完整矩阵、真实进程硬崩溃和业务争用未在本批穷举，主要依赖保留的围栏及快照机制和静态审查。逐检查点重建调用上下文证明数据库接续，不等同硬杀进程故障演练。旧 v4 测试不能自动充当新状态机的全部动态验证。
- App 基线错误为 `.next/dev/types/app/api/jobs/events/route.ts` 拒绝源路由额外导出 `createJobEventStreamResponse`；基线已有该导出且本批未改该路由，已单列 TODO。未绕过生成类型检查或放宽配置掩盖错误。
- 统一文档／图示检查及桌面验收由统筹者另行收口，本审查不提前认定完成。本批桌面只打开并关闭删除确认，不实际删除。
- PUBLISH 保留随作品数、候选数增长的同一事务成本；本批不声称全部数据库工作为常数成本。10 万、50 万、多业务争用、公开上限调整、真实库升级和生产发布均不在本记录通过范围内。
