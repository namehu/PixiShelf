# 旧归档快照画质核验修复

2026-11-05，用户报告生产历史核验已处理两千多部作品，全部显示未知。通过获准的 `pixishelf_diagnostics` 连接只读查询发现，当时已处理的 2,390 部全部被归为 `INVALID_MEDIA_SNAPSHOT`，尚未进入逐页交付证据判断。随后统计当前归档修订：3,093 部快照不含 `imageId`，669 部包含该字段。核验按作品 ID 递增执行，前一组先被处理。

Git 历史确认 `c1201716` 才向发布快照加入 `imageId`；更早的合法快照包含页序、相对路径、字节数、尺寸、SHA-256 和 MIME。核验代码直接复用要求 ID 必填的证据 schema，错误地把历史有效格式当成损坏。原单元测试的共享夹具始终带 ID，未覆盖真实旧格式。

## 生产只读证据与边界

- 旧样本作品 `16009`、`16022`、`16079` 合计 578 页，全部能按当前图片完整路径、顺序、大小关联，且与同一修订成功下载项的路径、SHA-256、大小、尺寸和 MIME 一致。
- 新格式样本 `21909` 的 232 页同样通过上述关联，快照包含 ID；最初全为未知时，任务游标尚未到该作品。后续生产规则版本 3 核验结果为 DISPLAY 232、ORIGINAL 0、UNKNOWN 0，核验时间为 2026-11-05 10:52:55.977 UTC。
- 三部旧样本的第一页都缺少最终下载地址及关联尝试记录。解决快照兼容后，它们仍须保持无法确认，原因应为 `NO_FINAL_SUCCESSFUL_ATTEMPT`，不能仅按 WebP 或宽度推断版本。
- 任务后来进入新格式作品时，已识别原图 13,061 页、网页阅读版 85,966 页（进度快照：已处理 3,330 部）；这些是当时累计进度，不是最终全库结果。
- 未导出生产完整 URL、带签名地址或媒体。批量详细重放改为生产只读聚合与脱敏合成夹具。全库下载证据完整性统计超时，未得到精确缺失总数，不将抽样结果推广为整库结论。

## 修复与恢复

核验输入兼容缺少 ID 的旧格式。仅当前修订能通过同一作品完整路径、页序、字节数唯一匹配 Image，然后继续执行成功下载、摘要、尺寸和 MIME 等原有检查。输出证据标注 `imageIdSource: CURRENT_IMAGE_PATH_ORDER_SIZE`，不会把推导身份写回原快照。显式 ID 冲突不回退，非当前旧快照无身份时不猜测或继承。畸形快照仍拒绝，原图升级复用的冻结身份要求不变。

画质规则版本升到 4，证据 JSON 保持版本 1，无数据库迁移。代码修复在本地完成，生产图片、下载记录及快照未修改。

发布修复后，应取消尚未结束的旧核验并等待终态，或者等旧任务完成，再从设置页发起新一轮全库核验。暂停后继续或失败后重试保留旧游标，不能作为从头重算。重算仅覆盖核验证据和汇总，仍缺下载证据的页会保留具体原因。

## 同批修复的 CI 历史迁移夹具

`v0.56.1` 的 CI 在 `artwork-dedup-review.postgres.test.ts` 的历史迁移回放用例失败：旧 SQL 函数依赖 `artwork_reading_summaries`，完整迁移链已将该表封存，导致预期的测试回滚异常之前先触发 PostgreSQL `42P01`。独立 PostgreSQL 15 空库完成全部 140 条迁移后复现了相同错误。

测试修复仅在回放所在事务创建包含所需三列及复合主键的临时旧表，事务结束自动移除。原迁移 SQL、生产 schema 和原有行为断言保持不变；该临时关系不进入部署迁移。这项修复与旧快照兼容修复一起准备发布为 `v0.56.2`。

GPT-6.1 Terra 在独立 PostgreSQL 15 上完成先失败后通过验证：目标用例 1 项通过，CI 相同五组数据库测试 60 项全部通过，执行器 `legacy zero-version` 匹配的 8 项全部通过（另 46 项因名称过滤未运行）。测试后旧 public 表不存在，当前 `artwork_dedup_group_choices` 函数摘要与测试前一致，140 条迁移记录完整；临时数据库容器已清理。
