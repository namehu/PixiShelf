# PixiShelf 产品基线

本文回答“PixiShelf 为什么存在、优先服务谁、必须守住什么，以及当前明确不做什么”。具体页面、字段和部署参数不在本文重复维护。

## 一句话定义

PixiShelf 是面向个人重度媒体收藏者的本地优先、自托管归档、整理、检索与浏览系统。

外部站点是收藏的输入和来源证据，不定义作品的本地身份；本地数据和用户整理结果在来源刷新、站点失效或项目升级后仍应保持可理解、可恢复和可继续维护。

## 目标用户

当前首要用户是：

- 长期积累大量图片、动画和视频的个人收藏者；
- 希望保留来源信息，同时拥有独立本地目录和整理权的人；
- 愿意在自己的 Linux/NAS/单机环境维护 Docker Compose 服务的人；
- 需要批量扫描、标签整理、媒体派生处理和故障恢复能力的实例管理员。

当前部署是单一信任域模型。系统可以存在多个账户，但已登录账户都等同实例管理员；这里的“单用户”不代表账户数只能为一，也不提供面向不可信用户或租户的权限隔离承诺。

## 用户需要完成的核心工作

1. 从本地目录、URL、Webhook 或辅助工具发现并导入作品。
2. 在保留来源引用的同时，为作品建立稳定、来源无关的本地身份。
3. 管理作品、媒体顺序、艺术家、系列、标签、来源快照和本地覆盖值。
4. 通过搜索、筛选、详情页和沉浸浏览使用自己的收藏。
5. 通过扫描、审计、后台任务和派生媒体处理维护收藏健康。
6. 在进程重启、任务失败、数据库升级或部署回滚后验证并恢复一致状态。

## 核心产品范围

### 收藏目录

- Artwork 是本地作品或作品包，可以包含多个有序 Media；
- Media 可以是图片、动画或视频；
- Series 用于组织多个有序 Artwork，而不是替代一个 Artwork 内的多媒体关系；
- Artist、Tag 和来源引用帮助检索与解释作品，但不替代 Artwork 本身的身份。

### 导入与来源

- 支持 Pixiv 目录扫描、本地目录导入、URL 归档、Webhook 触发和手工管理；
- 来源 Provider 与 Creation Method 分离；
- 一个 Artwork 可以保留多个可信来源引用；
- 无法可靠判断来源的历史数据保持 Unknown Origin，不默认猜测为 Pixiv；
- 来源刷新不能静默覆盖用户主动整理的值。

### 浏览与整理

- 提供作品、艺术家、标签、系列、详情和沉浸浏览；
- 支持图片、动画和视频展示；
- 管理面提供扫描、归档、媒体管理、批量操作、任务状态和审计历史；
- 桌面端是复杂管理操作的主要界面，移动端优先保证浏览和轻量整理。

### 后台处理

- 长任务通过 PostgreSQL 持久队列和单通用 Worker 执行；
- 扫描、归档、迁移、替换、维护和视频派生处理具有可恢复状态；
- scheduler 只物化计划任务，不直接执行业务；
- 视频封面、章节图和代表帧预生成后发布，用户请求不触发实时视频截帧。

## 产品不变量

以下规则优先于局部功能便利性：

1. 外部站点 ID 不能作为全局唯一的本地 Artwork 身份。
2. 原媒体、本地整理结果、来源映射和用户覆盖值属于不可轻易替代的数据。
3. 来源刷新可以更新来源快照，但不能无证据改写本地身份或覆盖用户整理。
4. 未完整验证的归档 revision 或派生媒体 generation 不能发布给正常浏览链路。
5. 删除、替换、迁移和恢复原媒体必须是显式、可审计且具备回滚依据的操作。
6. 数据库与文件系统构成一致性整体，备份和恢复不能只处理其中一侧。
7. 长任务不能依赖一次浏览器连接或 Next.js 进程内的 fire-and-forget promise 保证完成。
8. 生产稳态只允许一个通用 Worker 消费中央队列。
9. 可重新生成的缩略图和派生媒体不能反过来成为原媒体的唯一副本。
10. 当前事实、未来方案和历史实现必须在文档中明确区分。

## 质量优先级

当目标冲突时，按以下顺序取舍：

1. 数据完整性与可恢复性；
2. 身份、来源和用户整理语义正确；
3. 任务可观察、可取消、可重试和可审计；
4. 浏览与管理流程可用；
5. 查询和媒体处理性能；
6. 视觉一致性和交互精致度；
7. 新来源、新格式和功能数量。

性能优化不得绕过身份、权限、事务或文件发布不变量。UI 改造不得改变现有业务契约，除非另有功能规格和验收标准。

## 官方支持边界

当前支持基线：

- 单用户、单实例；
- Docker Compose/NAS/Linux 生产部署；
- PostgreSQL、宿主机文件系统、ImgProxy 和单通用 Worker；
- 通过受控反向代理和 HTTPS 访问；
- Chrome/现代浏览器 Web 界面，扩展能力按其包级说明维护。

当前两年内的非目标：

- 多租户、组织、复杂角色权限和租户级数据隔离；
- 社交动态、评论、关注、公开社区和内容分发平台；
- 面向第三方开发者承诺稳定的完整开放 API；
- Kubernetes、分布式集群、多个并行消费者和无限水平扩展；
- 由 PixiShelf 取代 PostgreSQL、NAS 或底层文件系统备份；
- 永久保证每个外部来源站点的抓取兼容性；
- 原生 iOS、Android 或桌面客户端。

非目标不是永久禁止。改变这些边界时必须先更新产品基线，并为架构和数据影响建立功能规格或 ADR。

## 兼容与演进原则

- 用户数据和可恢复性高于内部 API、内部表结构或旧实现兼容；
- 内部接口可以演进，但 expand、切换、观察和 contract/清理应分阶段进行；
- 数据库变更必须使用可审查的正式 migration；
- 破坏性清理与新功能切换不得放在同一不可回退发布中；
- 已发布功能变更必须说明迁移、验证和回滚边界；
- 未来方案使用 `draft`，只有完成实施和验证后才能并入 current 文档。

## 功能进入开发的门槛

以下任一条件成立时，应先创建短功能规格：

- 改变核心用户流程或产品边界；
- 涉及两个以上 workspace/package；
- 修改数据库结构、身份语义或数据生命周期；
- 包含异步任务、并发、重试、恢复或文件发布；
- 需要迁移、灰度或回滚；
- 预计实现超过 2–3 天；
- 验收标准无法在一个短 TODO 中说明。

普通样式、文案、局部组件和行为明确的小修复不需要单独 PRD。

## 产品级完成标准

一项中高风险功能只有在以下事项全部明确后才算完成：

- 用户问题、范围与非目标；
- 正常流程和异常路径；
- 数据、来源、权限和任务影响；
- 迁移、备份和回滚方式；
- 可执行验收标准和测试证据；
- current 文档已更新，草案和临时兼容信息没有伪装成长期事实。
