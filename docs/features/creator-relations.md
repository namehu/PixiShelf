# 艺术家、社团与作品关系

## 用户入口

- 艺术家列表可筛选艺术家与社团；详情汇总全部来源的有效关联作品。
- 作品详情列出全部创作者，时间线选择其中一个实体，不合并多个作者的作品流。
- 默认按来源发布时间排序，缺失时用入库时间，并以作品 ID 打破同时间并列；可切换入库时间。归档的来源时间是画廊发布时间，不表示原作创作时间。
- 作品编辑支持多选、清空归属和就地创建实体。作品管理选择作品后进入「修改作者或加入系列」，分别提供「自动填写作者」「手动修改作者」「加入系列」，每项说明修改效果。手动添加保留其他作者；移除不删除作品或作者资料。
- 管理艺术家中的「填写和纠正作品作者」进入 `/admin/artists/relations`。「自动填写作者」直接使用已保存的来源快照，不重新下载媒体；「纠正网站作者名」管理网站名称对应的本地艺术家／社团。
- 「先看看会怎么改」只生成检查记录，不修改作品归属；「确认修改全部 N 项」应用整份预览（包含其他分页），当前不提供逐项批准。发现误识别时需回作品管理缩小范围后重新检查。暂停或停止后续处理不撤销已保存的修改。
- 作者与系列检查使用独立页面，不嵌套在作品编辑或批量操作弹窗中。批量选择通过当前标签页的 sessionStorage 传递；选择丢失或无效时停止操作，不退回全部作品。单件入口在新标签页打开，保留未保存的编辑表单；检查记录 ID 保存在地址栏，刷新后可继续查看。
- 检查结果按作品分块显示名称、作者变化、依据与状态。简单的未填写作品显示「未填写 → 网站作者」；已有人工／来源关系或作者名称更正时，分别显示当前作者和网站标注，避免把原始标签误称为最终作者。旧 Worker 已保存的检查记录由读取接口转换为展示摘要，无需重新生成。
- 系列继续使用独立的 `SeriesArtwork`，一件作品可以进入多个系列，顺序在系列管理中调整。同作者与同系列具有不同含义。

## 身份与证据

`Artist.kind` 区分 `PERSON` 和 `GROUP`；类型创建后不通过编辑接口改变。多个来源可以指向同一实体，但同名不能证明同一人。

`ArtworkArtist` 对作品和实体唯一，`ArtworkArtistEvidence` 保存多个独立依据。只要至少一条依据满足 `present=true AND excludedAt IS NULL`，关系就有效。Prisma 使用 `activeCreatorMembership`，原生 SQL 使用 `effective_artwork_creators` 视图；计数和浏览均过滤已删除及非 ACTIVE 的归档。

来源依据为 `SOURCE`，人工追加为 `MANUAL`，迁移兼容依据为 `LEGACY`。保存未改变的来源成员不会自动转为人工归属；明确「追加」会建立人工依据。移除会排除该成员的已有依据，来源刷新不会自行取消排除。

E-Hentai 只采用明确的 `artist` / `group` 标签，分别建立来源标签映射，不把 uploader 当成创作者，也不解析标题猜测身份。来源标签按命名空间、trim 和小写归一化；同一来源标签复用映射。社团不能映射到 PERSON，艺术家不能映射到 GROUP。

来源快照中原始 tags 缺失与已确认空 tags 不同：前者可采用已保存的正向 SOURCE 标签；没有正向依据则报告 UNKNOWN。只有完整快照明确的空列表才能撤销该来源的旧自动依据。来源同步不删除人工依据。

来源标签更正会把该标签全部证据移至目标实体，保留每条证据的 present/excludedAt；其他标签及人工关系不动。历史和未来导入都遵循新映射。执行记录保留旧实体，支持「预览恢复原映射」，以当前版本重新确认，不盲目覆盖后续修改。

## 后台整理

`CREATOR_MAINTENANCE@v1` 在 `BACKGROUND_WRITER` lane 执行。入口要求中央调度已启用且存在支持该 capability 的新鲜 READY Worker。

`CreatorMaintenancePlan` 保存操作者、命令、范围上界、确认指纹；`CreatorMaintenanceItem` 保存每件作品的冻结来源／归属依据与结果。PREVIEW 每批最多 25 件，全部完成后变为 READY，APPLY 必须携带该预览指纹。预览对话框列出当前归属与准备执行的变更，每页 50 项。

APPLY 每批最多 25 项。执行前重验快照与人工归属指纹；变化的作品标记 STALE，要求重新预览；未知来源标记 UNKNOWN。自动创建的初始来源映射不会让同批后续作品误判过期，人工映射版本变化会使旧预览过期。

每批领域写入、逐项状态和队列终态／让行都在 Worker 租约保护事务中提交。暂停、取消不会回滚之前已提交的批次；重试继续 PENDING 项。页面关闭不影响任务。REMAP 是一次集合更新事务，映射版本和证据一起提交，不暴露半更新状态。

预览记录不自动过期清理；当前只提供最近 30 份记录入口。大型映射更正的事务耗时取决于关联数，若失败不会部分提交，可检查任务错误后重试。

## 兼容与部署

迁移 `20260908120000_unify_artwork_creators` 为旧 `Artwork.artistId` 建立 LEGACY 关系。INSERT 触发器为尚未改造的本地／扫描入口建立初始关系，UPDATE 不重新认领关系。现代 Pixiv 新建路径把新建的依据标为已验证 SOURCE；历史扫描刷新继续保留人工归属。

旧 `Artwork.artistId` 保留为历史兼容与存储身份参考；人工关系调整不改这个列，不移动目录，不更改 storageKey/storagePath 或媒体路径。数据库备份必须包括新表、视图、触发器和迁移记录。

升级前按[备份与恢复](../operations/backup-and-recovery.md)停止旧写入者并建立一致检查点，使用正式 generate/deploy 流程，禁止 db:push；App 与 Worker 一起更新。能力清单为 30 个 job type / 33 个 type-version 组合。首轮历史补全先生成预览，再确认执行。

只回滚二进制可保留新增表，但旧版读取 artistId，不能展示新人工关系；不要在混合版本下继续整理。需要恢复旧版完整语义时使用发布前一致检查点，不能把新增多对多归属压回单列后声称无损回滚。

本次迁移和关系测试使用独立 PostgreSQL 完成，业务数据库的部署和历史数据补全由实际升级流程执行。

## 验证依据

- 隔离 PostgreSQL 从空库部署完整 76 项迁移，新版 schema 门禁验证通过。
- 关系测试覆盖标签重放、缺失与空来源、人工排除、映射恢复、实体类型边界及存储身份保留。
- 维护任务测试覆盖跨批次冻结、暂停／取消后继续、依据过期和未知来源。
- 实际浏览器验证多创作者详情、选择社团、来源／入库时间切换、社团全部作品及缺少 READY Worker 时禁止提交。
- 主应用 lint、typecheck、生产构建及全量单元回归通过；独立 Worker 类型、构建及能力清单验证通过。PostgreSQL 领域回归另以隔离连接执行。
