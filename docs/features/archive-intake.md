# 归档收件箱

归档收件箱把 URL 采集、远端解析和媒体写入组织为可恢复的持久流程。管理员可以持续追加链接，默认“解析并归档”，也可选择“仅解析”。每件作品对应一个稳定归档任务，下载与发布由独立阶段执行；下载通道与其他媒体维护可以同时推进。

本文维护收件与下载规则；发现来源见[来源发现](./archive-discovery.md)，原子发布、维护与升级见[归档生命周期](./archive-lifecycle.md)，删除与恢复见[归档回收站](./archive-trash.md)。精确字段和 payload 以 Prisma、Zod 与共享契约为准。

## 页面与用户流程

| 页面                   | 职责                                                                       |
| ---------------------- | -------------------------------------------------------------------------- |
| `/admin/archive/inbox` | 批量追加 URL、管理发现来源、查看 FIFO 解析状态、修正、重试、取消与批量入队 |
| `/admin/archive`       | 服务端分页和筛选归档任务、查看明细、单项及当前页批量控制                   |

“添加链接”弹窗每次接受最多 100 行；服务端重新校验 URL、幂等键和活动收件容量。活动收件项目最多 1000 个。创建 submission 后请求立即返回，远端解析不占用浏览器或 Next.js 长连接。

收件项目平铺在全局 FIFO 中，submission 只标记一次提交和提供审计/筛选上下文，不形成必须等待全部完成的封闭批次。添加链接和人工勾选发现结果时，按次选择 `AUTO`（解析并归档）或 `MANUAL`（仅解析）以及 `ORIGINAL` 或 `DISPLAY` 画质；界面每次默认 AUTO/ORIGINAL。旧调用缺省模式仍为 MANUAL，数据库历史记录不自动启动。模式和画质参与提交幂等指纹，失败重试与修正链接继承原选择。

AUTO 模式的新作品解析成功直接创建下载任务；已有活动任务则关联并保留其画质；同一作品有变化时留在 `READY` 等待确认；未变化时进入 `SKIPPED`，不重复下载。MANUAL 模式保留解析后选项确认和批量入队。管理员可以在解析继续进行时选择待确认 `READY` 项并调整画质后入队；每项独立返回创建、复用、跳过、冲突或失败结果。原图不可用继续暂停，不自动降低画质；普通网络错误沿用现有重试策略。

远端返回 `REMOTE_NOT_FOUND` 的失败项目允许单项“直接重试”和勾选后批量重试，即使历史记录为 `retryable=false`。该字段仍控制自动重试，远端 404 不会自动反复请求；人工重试重新排队解析，继承原模式与画质，并保留任务关联和幂等、容量、活动重复检查。此错误仅表示当次远端请求报告不存在，不保证作品永久下架；其他不可重试错误仍须修改链接。旧失败记录无需迁移，升级 App 后即可人工重试，不会自动恢复。

解析结果区分新归档、更新、无变化、已有活动任务和重复来源身份。解析快照到期后不能直接入队，必须重新排队解析；修正失败 URL 会创建关联的新项目，不改写原审计历史。

E-Hentai 的扫描和收件解析均忽略标签、评分变化，不会仅因此推荐更新或要求重新下载；来源标签和评分仍保留在完整解析快照中。扫描继续比较标题、分类、上传者、发布时间、页数、文件大小、下架状态和版本关系，收件解析还比较图片页地址列表。解析及 AUTO 入队复核以当前已发布 revision 对应的来源快照为基线，完整 `metadataHash` 仍用于快照身份，不改写历史哈希、不回填数据库；缺少已发布基线时不猜测为无变化。

规则调整后，已有目录推荐与收件状态不会直接批量改写：重新扫描会更新目录分类，重新解析会更新收件分类；仅标签/评分变化的 AUTO 收件进入 `SKIPPED / UNCHANGED`，MANUAL 收件仍保留人工下载入口。发布须协调更新 App 和 Worker，无数据库迁移；回退原版本即可恢复原判断规则，既有快照与媒体保留。

发现来源的创建、扫描、筛选、绑定和人工接纳见[来源发现](./archive-discovery.md)。

任务页支持服务端 cursor 分页、状态/Provider/新建或更新/submission/文本筛选，以及 `PAUSE`、`RESUME`、`CANCEL`、`RETRY` 的当前页批量控制。批量命令逐项重新检查最新状态，不把部分冲突扩大成整批失败。回收、恢复、永久清理和 staging 清理仍走专用归档维护命令，不属于任务批量控制。

PC 任务列表使用紧凑表格，移动端使用精简卡片，默认展示标题、状态、来源、图片数量与简短时间。进度仅在运行态展示，失败或需要画质确认时展示处理提示；质量、重试次数、批次、完整时间和已发布媒体预览集中在任务详情。可用本地作品的标题进入作品详情，否则打开任务详情。“原站”入口在新标签页打开该次归档的规范化画廊页。

归档任务页的刷新、收件箱和添加链接操作集中在标题栏右侧；解析和媒体写入通道以简短状态和进度显示在标题区域。筛选工具栏独立于任务列表，滚动后吸附在后台导航下方；搜索、状态和归档类型常显，来源站点、本次加入 ID 和未绑定艺术家条件位于“更多筛选”。文本条件仍需提交，状态、类型和未绑定条件即时生效，切换筛选会重置分页与当前页选择。

已生效的任务筛选同步到 URL 的 `status`、`providerKey`、`kind`、`submissionId`、`search` 和 `unboundOnly` 参数；默认条件省略。刷新或打开同一链接恢复筛选，前进/后退恢复对应条件并重置分页与当前页选择；未提交的文本草稿不写入 URL。清除筛选仅移除这些条件，保留 `taskId` 等独立定位参数。非法枚举、布尔值或超出接口长度限制的文本条件按默认值处理。

当前下载默认收起为右下角浮球，点击展开实时速度、文件进度、暂停、取消和查看全部图片；浮层关闭不停止后台下载。浮球避开移动端底部导航和批量操作栏。展开后采用单列文件列表：顶部集中显示完成数量、总进度、速度和已下载量，文件名只显示一次，阶段、重试次数与字节数分行对齐；暂停、取消和查看全部图片固定在底部，内容超高时仅中间区域滚动。手机端直接展示文件进度，不再要求二次展开；断线时聚合与逐文件速度均隐藏，保留最后采样的数量与进度。任务项将来源和艺术家合并为紧凑副行，已绑定及待生效的艺术家名称可进入艺术家详情，待生效关系保留明确标记；“管理艺术家”收进任务操作菜单，详情内的管理入口仍保留。任务排序、状态安全检查、确认流程与绑定规则不变。

## 任务进度与实时更新

归档任务页通过 admin layout 中唯一的通用 Worker SSE 连接接收生命周期与 `archive.transfer@v1` 遥测。速度由 Worker 在媒体流写盘时累计 chunk 长度并按最近 5 秒采样，不保存 chunk、也不回读磁盘。遥测还携带当前最多 8 个媒体 worker 的页码、预期文件名、尝试次数、阶段、已接收字节和可用时的 `Content-Length`，不携带图片页、CDN 地址或 provider token。页面在通道状态下方只为当前 `ARCHIVE_DOWNLOAD` 展示聚合进度和逐文件活动槽位；任务行仅运行时显示稳定总进度，完成后显示状态与图片数量，完整图片历史仍从任务详情按 PostgreSQL 分页读取。SSE 正常时列表只做 30/60 秒一致性校准，图片明细在计数或状态变化时定向刷新；连接异常自动回退原有高频轮询。

## 批量收件的事务预算与诊断

发现结果“加入收件箱”和直接提交 URL 均支持一次最多 100 条，使用专用交互事务预算：
`timeout = 30_000ms`、`maxWait = 5_000ms`。后者是获取事务连接的等待上限，不是数据库锁等待上限；
事务内锁等待计入前者。HTTP 总耗时还包含连接等待、输入处理和响应传输，不能把 30 秒当作整个请求的硬上限。
其他事务、Worker 并发和全局 Prisma 配置不变。

提交中的 submission、收件、解析任务、初始事件和发现目录回写在同一事务内提交或回滚。
无效、重复或容量不足的输入沿用原有分类计数，原子性不意味着绕过这些规则全部接受。
删除记录和活动 URL 查重采用批量读取，任务、收件和事件批量创建，发现目录按作品身份批量回写到所有来源。
FIFO 使用数据库序列按原输入处理顺序显式分配；发现结果仍按目录 ID 顺序处理，回滚后的序列空洞不影响顺序。
重放相同提交编号仍校验请求指纹和操作者，返回原 submission，不重复创建任务或将已推进的目录状态回退。

解析和下载运行期间可以提交。除了同一来源或作品身份的竞争，`system_jobs` 的
`artist_job_command_guard` 触发器也会获取创作者目录锁 `7341902118`，与解析完成、归档发布共享；
因此不同作品也可能在创建解析任务时等待。收件服务在任务插入前显式获取同一把锁用于计时，
不移除触发器保护、不改变已有锁的相对顺序，也不要求暂停后台任务。
数据库不可用、锁持续占用超过预算或真实业务冲突仍可能失败；失败不提交部分收件。

App 输出 `Archive intake submission completed` / `Archive intake submission failed`，
包含 `operation`、`submissionKeyHash`（原提交键的 SHA-256）、`itemCount`、`outcome`、
`durationMs` 和 `phasesMs`。阶段包括 `transactionWait`、`sourceLock`、`identityLocks`、
`idempotencyLock`、`capacityLock`、`creatorCatalogLock`、`stateChecks`、`intakeWrite`、
`serialization`、`catalogWrite`；失败还包含 `failedPhase`、异常类型、错误码和脱敏消息。
日志不记录完整 URL、Cookie 或请求体，前端保持通用错误提示。

排查时先用 `docker ps` 核对实际容器名，再读取 App 日志。日志中 `creatorCatalogLock` 较长说明等待共享目录锁，
`identityLocks` 较长说明作品身份锁等待；不要仅凭有下载任务运行就认定网络下载持有长事务。

本修复无需新增 migration。发布前记录实际 App/Worker 镜像 digest 与现有备份恢复点，
保留兼容的旧 App 镜像供回退；回退不删除收件、任务或媒体。隔离 PostgreSQL 验收覆盖 100 条 FIFO、
容量竞争、幂等、失败回滚、超过 5 秒锁等待、30 秒事务超时，以及真实解析/下载执行器在传输、
检查点和发布阶段的三轮并发提交；外网 Provider 使用受控 fixture。线上 NAS 性能和反向代理行为
仍需部署后用真实需要收件的 100 条验证，不能用本机测试耗时替代线上验收。

既有隔离验证与限制见[收件验证记录](../records/features/archive-intake.md)。

## 失败收件的原站核实与删除

收件 URL 可在新标签页打开当时提交的原始地址，不要求解析成功；仅对通过 HTTPS、Provider 主机、端口、凭据与支持路径校验的地址生成链接，非法地址只显示文本。链接保留隐私遮蔽，使用 `noopener noreferrer` 和 no-referrer。

收件箱失败项与发现来源中符合条件的失败项支持单项和批量“删除失败记录”。人工确认后删除同作品全部失败收件、所有来源对应的目录项及扫描结果明细；已有本地作品、媒体、下载任务、SystemJob/事件、提交批次、幂等回执和来源游标保留。旧扫描的计数快照不重写。收件已被 30 天清理、仅剩来源失败摘要时也可处置；活动或失败下载任务须先在归档任务处理。

删除逐作品执行事务，复用来源、发布、身份/URL、收件容量及行锁；相关来源活动扫描、同作品活动收件/下载、失败下载或请求后状态变化会阻止该项删除。支持批量部分成功和逐项结果；网络重放沿用原请求边界，不删除后来提交的失败。删除成功刷新收件、侧栏和发现统计。旧任务日志不能重新创建已删除收件。

不新增已处理状态或屏蔽名单。未来扫描重新返回该作品时可重新发现。此操作不可撤销；正式使用前应具备数据库备份，恢复旧发现明细需按备份恢复基线从数据库备份恢复，不影响媒体文件。

发布先执行 `20261007000000_delete_archive_failed_records` migration deploy，再升级 App；迁移仅扩展既有批量命令枚举 `DELETE_FAILED_RECORDS`，不删除历史数据、不改变 Worker payload，无需 Worker 同步升级。回退 App 可保留新增枚举，但不会恢复已经人工删除的条目。上线前在隔离库验证完整迁移链及删除回归，不使用 db:push。

既有隔离验证与限制见[收件验证记录](../records/features/archive-intake.md)。

## 阶段与控制

归档列表与任务中心按 `ArchiveImport.id` 聚合为一项，服务端在分页和计数前只选择当前阶段。展示依次为等待下载、下载中、校验中、等待入库、入库中、完成；交接进度保持 95%，只有实际发布后达到 100%。详情可展开阶段和重试记录，SSE 按稳定归档身份跟随当前执行，阶段交接不触发整项成功通知。

旧、新归档任务都通过领域控制暂停、恢复、取消、重试；历史 job ID 不得误控制当前阶段。等待发布也可以暂停/取消；下载失败仅补未完成文件，发布失败仅重试发布；文件封存后不允许切换展示画质。画质、默认标签和来源在入队时冻结，交接不重新读取配置。自动阶段为 SYSTEM / 900，人工阶段为 MANUAL / 10，均不抢占已经运行的任务。

## 下载明细地址

E-Hentai 媒体项的后续下载尝试会读取图片页 `loadfail` 入口中的 `nl` 参数，在同一图片页追加该参数请求一次刷新，再解析新媒体地址。只读取有界参数，不执行远端脚本；缺少或非法参数时沿用普通解析。每次尝试最多增加一次受 Provider governor 管理的页面请求，总下载尝试次数、退避、取消与原图/展示质量规则不变。刷新是请求原站重新分配来源，不能保证每次都会分配不同节点。人工重试重置次数后先进行普通下载，仍失败则后续尝试刷新。

媒体下载流同步计算 SHA-1；仅当最终 HTTPS H@H 文件地址具有已识别的 `/h/` 或 `/om/` 文件摘要路径时，与该表示对应的摘要比对，不使用图片页 token 代替文件摘要。`/om/编号/原图描述/派生图描述/...` 使用派生图摘要；第四段为 `x` 时使用原图摘要，无法识别时不猜测摘要。长度正确但摘要不一致的内容仍拒绝保存，并作为可重试媒体损坏处理。正常图片继续执行现有大小、尺寸和首帧元数据校验，不降低图片校验要求。

下载明细逐项显示完整图片页地址和最近记录的实际下载地址，支持复制与打开。下载地址来自 Provider 收到成功媒体响应后的最终 URL，保留路径、端口和 query；记录发生在流传输与图片校验之前，因此这两个阶段失败仍可查看地址。记录同时显示尝试次数、时间及可能过期的提示。请求尚未成功建立、旧版本未记录或地址无效时显示“尚未记录”，不能从远端主机名反推原地址。旧记录可打开图片页排查，或重试此图生成新的下载地址。

旧记录没有实际下载地址，不能从 `remoteHost` 反推；优先打开保留的图片页排查。

`20260916200000_archive_item_download_urls` 为 `ArchiveImportItem` 增加可空 `lastDownloadUrl`、`lastDownloadAt`、`lastDownloadAttempt`；不回填历史直链。新尝试领取时清空旧记录，响应后在任务租约保护下写入，每项仅保留最近一次。部署需先按备份恢复基线建立检查点并执行 migration deploy，再升级 App 与 Worker。回退应用时可保留这三个可空字段，不应通过删列恢复。数据库中完整地址属于敏感诊断数据，仅在认证下载明细返回，普通事件和错误继续脱敏。

## E-Hentai 版本关系与归档身份

版本关系来自解析时 `gdata` 返回的上一版/当前版字段，不是解析与下载之间的前后差异比较，也不是实时更新通知。
仅存在上一版表示该画廊有历史版本；远端当前版 ID 与提交链接的画廊 ID 不同时，才表示解析时另有新版。
一个中间版本可以同时关联上一版和新版，不能因为发现上一版就把当前链接视为过时。

归档下载沿用已冻结的链接和媒体计划，不因版本关系自动切换目标或追加下载。若需要新版，管理员应另行添加新版链接、
解析并确认归档；不同画廊 ID 创建独立作品，双方存在时记录 `REPLACES` 关系，不覆盖、删除或合并旧作品。
这与同一 Provider/外部 ID 的快照更新是两种不同情况。

## 持久状态与恢复

核心持久结构包括：

- `ArchiveIntakeSubmission` 与 `ArchiveIntakeItem`：保存输入、FIFO 顺序、解析状态、冻结结果、下载模式、画质、重试/取消 intent 和归档关联；
- `ArchiveBulkOperation` 与逐项结果：保存批量入队和任务控制的请求者、幂等键、目标与结果；
- `ArchiveUploaderSource`、`ArchiveUploaderScanRun` 与 `ArchiveUploaderScanItem`：保存上传者身份、双向游标、人工扫描状态、分类结果和收件关联；
- `SystemJob.executionLane`：把解析工作和所有媒体写工作映射到固定资源通道；
- Worker lease、heartbeat、attempt 与 `leaseToken`：为领取、进度和终态提供数据库执行围栏。

收件队列暂停只阻止领取下一项，不中断当前解析。取消当前解析使用持久 intent 和 cooperative abort；瞬时错误按退避策略重试并重新进入队尾。浏览器刷新、App 部署或 Worker 重启不会丢失 FIFO、attempt、暂停状态或已完成的批量结果。

自动入队在 resolver 的 fenced 终态事务中调用 App 手动入队共用的核心实现，原子提交解析结果、下载任务与事件。发布锁下重新判断已有归档与活动任务，避免并发发布后误将新建变成自动更新；媒体下载由独立下载通道执行，封存后原子交接给 writer 发布。`SKIPPED` 属于终态，归入取消/跳过历史及既有 30 天保留清理。

解析、发现来源和下载共享 Provider 请求间隔与真实限流冷却；普通请求默认间隔 250ms，搜索请求获准后设置 3 秒间隔。活跃下载许可只限制下载并发，不再使解析退队。因此前一作品下载时，后续作品可以继续完整解析并自动入队，无需等待媒体流结束。真实站点限流仍按既有策略重试；共享请求机会不保证严格轮转或防饥饿，下载请求可能因解析请求而稍后获准。下载流的许可仍持续到流结束，并保持续期与过期回收。

## 归档任务的艺术家绑定管理

`/admin/archive` 的桌面任务表格、移动卡片与任务详情按 `providerKey + externalId` 展示实际已绑定和待生效艺术家／社团；不把来源默认配置或旧 `Artwork.artistId` 当作当前绑定。列表最多展示 3 位及剩余数量，详情展示完整名单，名称遵循隐私模式。手动链接产生、没有发现来源目录记录的任务也支持此能力。

“仅看未绑定艺术家”要求同时不存在待生效记录和有效作品的生效关系，在数据库分页前执行，并与状态、来源、归档类型、提交批次和搜索条件组合。直接按任务 ID 读取详情不继承列表筛选。

“管理艺术家”支持单条追加和逐项确认移除，不提供任务批量绑定。未归档（包括失败、取消）时追加为待生效，已发布时立即更新当前作品；不会启动下载，也不修改来源默认配置。同一原站身份的其他任务和来源共享结果。回收站作品、非 ACTIVE 作品及正在清理的任务拒绝编辑。移除沿用手动抑制，阻止发现来源自动补回；显式追加可以恢复绑定。

`archive.editTaskCreators` 为管理 mutation，仅接受任务 ID、ADD/REMOVE、最多 200 个艺术家 ID 和 UUID 请求编号；身份与操作者由服务端取得。事务按既有创作者→发布→原站身份锁顺序重读当前发布状态，避免提交期间发布完成导致移除遗漏。操作复用永久保留的 `BIND_CREATORS` 回执，指纹包含 ADD/REMOVE 和规范化的艺术家列表。网络结果未知时保留原编号（含当前浏览器会话恢复），已知失败后重试生成新编号。回放旧追加回执不会恢复后来已移除的绑定。

本次无数据库迁移、文件写入或 Worker 协议变化。回退 App 可恢复旧页面，已保存的关系和抑制记录继续遵循既有发布规则；需要撤销具体关系时使用显式追加／移除，不删除回执或通过重放请求恢复。发布验证使用独立临时 PostgreSQL 空库部署现有迁移，不操作业务数据库或真实媒体。

## 权限与敏感数据

两个页面都需要 Better Auth Session。`archiveInbox`、`archiveUploader`、`archiveSearch` 和 `archive` 的读取使用 `authProcedure`，创建来源、扫描、来源停用/启用/删除、结果入箱、暂停/恢复、取消、重试、批量入队和任务控制使用 `adminProcedure`；当前单一信任域中二者运行能力相同，但敏感写操作保留显式管理员语义。

服务端负责 URL/行数/容量上限、Provider HTTPS allowlist、DNS/redirect/SSRF 防护、响应体限制、状态 CAS 和幂等约束。已认证的归档收件接口完整返回收件项目的 `submittedUrl` 和 `canonicalUrl`（包括路径及查询参数），用于核对和排错；列表与创建、修正等返回收件项目的响应使用同一规则，尚未解析的 `canonicalUrl` 保持 `null`。收件列表的提交地址自动换行显示，仍遵循隐私模式。其他归档列表、事件、日志和错误继续脱敏，不返回 Cookie、Authorization 或完整 Provider locator。

`GET /api/archive/tasks/[id]/source` 在验证会话后从任务读取 canonical URL，只接受与任务 GID 一致的 E-Hentai HTTPS 画廊地址，返回禁止缓存的重定向并设置 `Referrer-Policy: no-referrer`。客户端不能指定重定向目的地；归档下载任务列表仍使用脱敏地址，通过用户主动打开原站时的重定向提供完整地址。
