# 后台任务失败诊断

任务详情提供具体失败原因、原因分组和全部已记录失败对象，供管理员判断哪些对象需要修复。本文描述当前仓库实现，不代表已经完成生产部署或恢复演练。诊断不会改变原有任务状态、取消、暂停、重试条件和业务发布规则；原本“已完成但部分失败”的任务仍保持 COMPLETED，并显示部分失败记录。

## 独立执行与冻结

每次领取任务生成独立的诊断 execution ID，存入 SystemJob.currentDiagnosticExecutionId。它与租约 executionToken、任务 ID 和 attempt 分开；即使一次让行保留 attempt，下一次领取也使用新的诊断 ID。报告在首次记录诊断时创建，以该 ID 为主键，不为完全没有诊断的执行强制创建空报告。

SystemJobDiagnosticReport 保存所属任务、attempt、执行结果、完成标记、对象计数和保留时间；SystemJobDiagnosticItem 保存任务级原因或逐项对象证据。任务级条目使用 TASK，失败对象使用 ITEM，报告的对象数量不包含 TASK。父任务通过失败子任务链接进入子任务报告，不复制子任务的全部明细。

诊断写入与对应领域检查点处于同一个 fenced transaction，事务开始和提交前校验任务租约。Dispatcher 还绑定本次诊断 execution ID，旧执行不能把迟到诊断写进后续领取的报告。终态结算关闭报告，之后重试不会覆盖旧报告。关机释放、暂停、取消、租约失效或诊断采集未完成的报告会标明不完整；已有条目仍可用于排查，不应当成全任务完整失败清单。

| 来源      | 含义                                     | 去重规则                                 |
| --------- | ---------------------------------------- | ---------------------------------------- |
| CURRENT   | 本次执行实际观察并持久化的失败           | 同一报告使用稳定对象 key 去重            |
| INHERITED | 从领域持久检查点复制的、仍未恢复的旧失败 | 同 key 的 CURRENT 优先；不冒充本次新失败 |

归档媒体失败在终止该项的 CAS 事务内记录页码、文件名、尝试次数、阶段和错误证据；启动时仍为 FAILED、不会进入本轮下载的旧项，每批最多 100 项重新读取并冻结为 INHERITED。最终归档结算不在一个长事务内遍历全部失败。分批中断保留已提交证据，下一次执行重新收集仍存在的旧失败。

扫描、本地导入、迁移、替换、媒体派生及维护的逐项记录沿用各自领域失败检查点。操作失败导致的关联项终止，与真实对象失败使用不同原因标注；取消不伪装成新发生的媒体或网络错误。领域结果原有的前 20 条样例可继续用于轻量摘要，统一诊断明细不沿用该截断上限。

## 查询与旧数据

诊断报告和对象均通过管理员 tRPC 接口读取：

- job.backgroundDiagnosticReports 按任务查询执行报告，使用 createdAt/id 游标倒序分页；失败子任务单独分页。
- job.backgroundDiagnosticItems 校验 reportId 属于 jobId，按明细 ID 游标分页，并可按 reasonKey 筛选；原因分组统计针对整份报告。
- 报告和对象单页默认 50 条、最多 100 条。单页上限不是保存上限，继续加载可读取全部已记录对象。它也不受任务 Dashboard 最近 10 条限制。

升级前没有独立执行快照的数据，不能补造为历史完整报告：仍绑定原任务的归档检查点可提供当前逐项视图；只留 failedSamples/failures 的旧任务只能显示已有样例；只有任务摘要的记录明确表示没有逐项证据。旧检查点会随业务恢复变化，不是不可变的过去执行。存在新报告（包括已经过期的报告）时，不能通过 legacy 查询绕过保留规则或把当前检查点冒充旧快照。

## 具体原因与敏感信息

归档下载完成后的图片检查只读取首帧元数据（`pages: 1`），不加载全部动画帧来累计像素；因此正常多帧 WebP 不会仅因总帧数触发 Sharp 默认像素限制。单帧像素上限、字节上限和无效图片头检查仍保留，原文件字节、动画帧和 SHA-256 不变。此检查不是完整逐帧解码校验；后续实际解码任务仍须执行各自的资源限制。258 帧、每帧 1024×1024 的 WebP 回归样例覆盖旧路径超限、新路径归档成功与字节一致性。

诊断保留经脱敏的实际原因，以及有界原因链中的域错误码、底层 errno、HTTP 状态、经过校验的远端主机和阶段。普通错误没有底层错误码时仍保留可安全展示的实际消息；建议信息用于辅助排查，不改变重试策略。

写入和展示均进行脱敏，不保存原始堆栈、完整远端 URL、代理凭据、Cookie、Authorization、Token 或 SQL 文本。远端地址只允许经过校验的主机及端口，不包含账号、路径或查询参数。绝对路径隐藏目录部分，仅保留 basename，结合对象身份、阶段和文件名定位，不暴露本机目录布局。文件名、目标信息、作品信息和错误详情仍使用隐私敏感文本包装，在隐私模式下遮蔽；隐私模式不能替代会话鉴权。

接口沿用 adminProcedure 的有效会话边界，并复核任务与报告归属；不存在匿名诊断接口。通用 SSE 只同步轻量摘要和报告标识，不携带逐项明细、完整错误证据、payload、result 或租约 token。诊断详情按需从受保护接口查询。

## 保留与清理

报告关闭后，明细证据保留 90 天。JOB_EVENT_RETENTION_CLEANUP 同时处理到期诊断：只选择 CLOSED 且到期、未标记过期的报告，每次事务最多删除 5,000 条明细；全部明细清理后设置 expiredAt。中断后从剩余明细继续，不重新打开报告。

报告头和原有计数继续保留，界面可说明“证据已过期”，不会把明细为空解释为没有失败。关闭报告到达 expiresAt 后，API 即停止返回明细、原因分组和任务级证据，即使清理计划尚未运行或正处于分批删除中；报告头和计数仍可读取。物理删除由实际启用的清理执行完成，计划停用时不会仅因时间经过自动删除。既有事件分层保留仍为普通 INFO 进度 7 天、阶段/警告/错误/控制/终态 90 天。首次手动清理使用 dry-run，核对诊断报告与明细候选数后再启用计划删除。

## 发布与恢复

正式迁移为 20260916160000_job_diagnostics，新增可空执行 ID 及诊断报告、明细表，不推断或回填旧执行证据。发布必须依照[备份与恢复](../operations/backup-and-recovery.md)建立停写一致性检查点，保存数据库 dump、媒体快照、配置和旧 App/Worker 镜像的对应关系。

停止写入者后执行 pnpm --filter @pixishelf/db db:generate 和 pnpm --filter @pixishelf/db db:deploy，核对 migration 状态，再协调启动兼容该迁移的 App 与 Worker。禁止用 db:push 替代正式迁移，也不能只升级 App 并期待旧 Worker 生成完整诊断。首次清理应先确认 dry-run 范围，避免发布与证据删除同时发生。

回滚优先采用兼容版本或前向修复，保留新增列、报告头及明细表，不能通过删表或清空报告回退界面。旧 Worker 不写新诊断，应明确回滚期间的采集缺口。需要恢复发布前数据库时，按同一完整备份集合配对恢复媒体和配置，并明确检查点之后的新诊断及领域写入会丢失；恢复前保全现有证据。

## 验证边界

验收至少覆盖：独立 claim 与保留 attempt 的分离、CURRENT/INHERITED 去重、租约丢失零写入、结算原子性、13 项和超过 20 项完整采集、归档跨 100 项分批与中断、真实 errno/HTTP/错误消息、报告归属鉴权、分页/筛选、旧记录限制、90 天边界及 dry-run/中断清理。

聚焦单测和类型检查不能证明生产 migration、真实 PostgreSQL 竞争、浏览器隐私显示或 NAS 行为。发布记录应分别登记隔离库迁移与事务测试、App/Worker 构建、真实浏览器检查、清理 dry-run 和备份恢复证据。本文不宣称这些生产演练已经完成；具体命令结果以本次交付和部署记录为准。
